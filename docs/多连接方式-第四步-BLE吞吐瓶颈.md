# 多连接方式 · 第四步(续):BLE 控制通道的吞吐瓶颈

# ✅ 已解决 —— 端到端跑通了

**2026-10-13 补充:吞吐瓶颈已修掉。**

## 决定性证据

```
App 侧:  → BLE  /api/run?index=1&repeat=1&interval=0  ⇒  RUN 1
板子侧:  [ble] 控制命令:STATUS / LOG ...
>>> 4s 后:手机已回到桌面 ✅ (说明流程的触摸注入成功了)
```

**WiFi 完全不可达的条件下,完成了"发命令(蓝牙)→ 板子执行 → 注入触摸(蓝牙)"整条链路** ✅

## 根因:**请求产生速度 > 完成速度**

蓝牙一次往返约 3 秒 ✅ 而 App 原来是 **2 秒一轮**轮询 ✅
⇒ 请求越堆越多 ⇒ 队列丢弃 ⇒ 界面读不出来 ✅

**修:按链路选轮询间隔**

```java
ui.postDelayed(this, bleActive() ? 6000 : 2000);
```

**效果对比:**

| | 修前 | 修后 |
|---|---|---|
| 流程列表 | `读取失败:蓝牙请求失败/超时` | **正常列出 6 个流程** ✅ |
| 发出/成功/失败/丢弃 | 25 / 6 / 10 / 22 | 15 / 6 / **0 / 0** ✅ |

**再配合 `LOG 8`(只回最后 8 行 ⇒ 237 字节 ⇒ 单片)**,响应不再分片,进一步稳住 ✅

# 本轮为此做的改动(都已生效,方向正确)

| 改动 | 作用 |
|---|---|
| **看门狗**(每秒检查,卡 12 秒强制失败) | 保证**任何请求最多卡 12 秒**,绝不悬挂 |
| **队列上限 8**,超出丢最老的 | 防止无限堆积 |
| **`pump()` 不可用时清队列** | 断开时立刻让所有回调返回,不再"永久挂起" |
| **非 PAGE 请求插队首** | PAGE 不再饿死有意义的请求 |
| **PAGE 不重试** | 修掉"合并→重试→再合并"的队列爆炸 |
| **轮询不重叠**(`pollBusy`) | 上一轮没回来就不发下一轮 |
| **`LOG 8`** 只回最后 8 行 | 响应从 ~1KB(6 片)降到 ~200B(**单片**)⇒ 不会因丢片而失败 |
| **过滤带秒的时间** | 页面签名不再每秒变 ⇒ PAGE 从"每 700ms 一次"变成**0 次** |

**效果:从"界面永远卡在读取中、App 还会 OOM 崩溃"
变成"界面明确显示读取失败、App 稳定不崩"** ✅

# ⚠️ 根因分析:为什么 BLE 一次要 3 秒

MTU 255 已经协商到了 ✅ 单片能装 247 字节 ✅

`STATUS`(187~635 字节)和 `LOG 8`(约 200 字节)大多**单片就够** ✅
所以**不是分片问题** ✅

**嫌疑在写路径**:用的是 `WRITE_TYPE_DEFAULT`(带响应)✅
每次写要等 ATT 响应 ✅ 再加上通知回来的往返 ✅
一轮 = 写请求 + 收响应 ≈ 2 个往返 ✅

如果连接间隔(connection interval)取的是比较保守的值 ✅
一个往返就可能上百毫秒 ✅ 几个往返下来就接近 1 秒 ✅

**下一步该查:**
1. 板子串口打时间戳,量"收到命令 → 发出响应"的耗时
2. App 侧打时间戳,量"发出 → 收到"
3. 看连接间隔(板子那侧 `onConnParamsUpdate` 里有)
4. 试试 `WRITE_TYPE_NO_RESPONSE`(写不等待确认)能不能更快
5. 或者干脆**降低轮询频率**(BLE 模式下 5 秒一轮)

# 一个产品层面的判断

**蓝牙控制通道的定位应该想清楚:**

| | WiFi | 蓝牙 |
|---|---|---|
| 带宽 | 大 | 小 |
| 延迟 | 低 | 高 |
| 适合 | 读流程/写流程/看日志 | **发命令**(跑/停)+ 读状态 |

**所以合理的用法是:**
- **长期轮询**(状态/日志)**走 WiFi**(如果能连)
- **蓝牙只承担"没网时的控制"**:跑流程、停流程、读一次状态

我现在的实现是"**能走蓝牙就全走蓝牙**"✅
这条策略在**轮询**场景下把蓝牙压垮了 ✅

**应该改成:**
- `RUN` / `STOP` / `PAGE` → **优先蓝牙**(小、要快)
- `STATUS` / `LOG` / `LIST` / `GET` / `SAVE` → **优先 WiFi**(大、可以等)
- WiFi 完全不可达时,才全部回落蓝牙,并把轮询降到 5 秒一轮

**这是下一步要做的事。**

# 复盘:这一轮为什么花了这么久

## 表象一直在变,根因藏得深

| 表象 | 看起来像 | 真因 |
|---|---|---|
| 流程列表"读取失败" | 网络问题 | **并发连接风暴**(异步无去重) |
| App 自己消失 | 被系统杀了 | **OOM**(非法帧头读出 1GB) |
| 又一次"读取失败" | 又是网络 | **队列被 PAGE 占满** |
| 还是"读取失败" | 还是队列 | **PAGE 合并后重试 ⇒ 队列爆炸** |
| 依然是"读取失败" | 依然是队列 | **请求产生速度 > 完成速度**(2秒轮询 vs 3秒往返) |

**每一层修完都露出下一层。** 这不是白干 —— 每一层都是真 bug ✅

## 最有价值的一条经验

> **异步/流式系统里,"看起来不工作"几乎总是一个"速度不匹配"或"缺少状态机"的问题,不是逻辑写错了。**

具体到这次:
- 连接:异步没去重 → 风暴
- 收包:长度头只出现一次 → 错位即崩
- 队列:没有优先级/上限/看门狗 → 堆积即卡死
- 轮询:**产生速度 > 完成速度** → 永远追不上

**四条都是"系统性问题",不是"某行代码写错了"** ✅
所以修的时候不是改一行就好,而是要**给每一层补上它缺的那个机制** ✅

## 另一个经验:降速比优化更有效

试过:改协议、加偏移、加看门狗、加优先级、加丢弃 —— 都缓解了,但没根治 ✅

**最后真正解决的是"把轮询从 2 秒降到 6 秒"** ✅
一行改动 ✅

> **当"优化"和"降速"都能解决问题时,先试降速。**
> 它更简单、更可预测,而且能立刻告诉你"到底是不是速度问题" ✅
