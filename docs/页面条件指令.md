# 页面条件指令:waitfor / ifpage

## 为什么需要

以前只能 `wait 3000` **猜**页面加载完了,然后按坐标点。
页面慢一点就点空,而且失败了完全不知道为什么。

现在可以:
```
waitfor 预约想看票档 10000     # 等到出现再继续
ifpage NcovSkuActivity         # 按页面分支
```

---

## 语法

| 指令 | 写法 | 说明 |
|---|---|---|
| 等待页面 | `waitfor <关键字> [超时ms]` | 等到页面上出现关键字,默认最多 15 秒 |
| 如果是页面 | `ifpage <关键字>` | 匹配则继续,否则跳到 `else` / `endif` |
| 否则 | `else` | 上一支不成立时走这里(可省略) |
| 结束判断 | `endif` | 必须和 `ifpage` 配对 |

### 关键字规则(故意做得宽松)

- **包含匹配**,不用写全
- **忽略大小写**
- 不加前缀 → **Activity 类名和页面文字都找一遍**
- 加 `@` 前缀 → 只匹配 Activity
- 写 Activity **短名**就行(`NcovSkuActivity` 能匹配全类名)

### 示例

```
waitfor 青岛 5000
ifpage ProjectDetailActivity
    T 0.5 0.5 60 详情页点中间
else
    T 0.5 0.9 60 其他页点底部
endif
T 0.5 0.5 60 收尾点击
```

支持**嵌套**(最多 16 层)。

## 实测(两个场景都跑通)

### 场景 A:页面是详情页

```
[1/7] 等待页面:青岛
  → 页面已出现(等了 1 ms)                    ✅ 关键字命中
[2/7] 如果是页面:ProjectDetailActivity
  → 匹配,继续                                ✅ 走第一支
[3/7] 点击:在详情页点中间
[4/7] 否则
[7/7] 点击:收尾点击                           ✅ else 正确跳到 endif
[script] 完成:5 步,耗时 202 ms
```

### 场景 B:页面是首页(不匹配)

```
[1/7] 等待页面:青岛
  → 超时,继续执行(等了 5041 ms)              ✅ 优雅超时,不报错
[2/7] 如果是页面:ProjectDetailActivity
  → 不匹配,跳到第 5 步                        ✅ 跳过第一支
[5/7] 点击:不在详情页点底部                    ✅ 走了 else
[6/7] 结束判断
[7/7] 点击:收尾点击
[script] 完成:5 步,耗时 5228 ms
```

> **超时的设计**:`waitfor` 超时后**继续往下走**,不报错。
> 因为流程设计者可能只是"希望"等到,而不是"必须"等到。

## 架构:为什么绕了一圈

```
手机 App(无障碍)  ──POST /api/page──▶  ESP32 板子(脚本引擎)
   知道当前页面                          执行 waitfor / ifpage
```

**脚本在板子上跑,但页面识别在手机 App 里** —— 所以 App 要把页面推给板子。

### 推送时机(两种)

| 时机 | 目的 |
|---|---|
| **页面一变就立刻推** | 脚本**开头**的 `waitfor` 不用干等 |
| **流程执行中每 700ms 推** | 页面上的文字会变,`waitfor` 靠它判断 |

空闲且页面没变时**不推** —— 省电也省板子的 CPU。

### 板子侧新增

- `POST /api/page?act=&text=` —— App 推页面
- `/api/status` 里新增 `page` 和 `pageAt`(便于排查)

## ⚠️ 踩到的坑:MIUI 的无障碍会卡在「正在绑定」

调试时遇到:设置里显示**已启用**,但 `dumpsys accessibility` 里

```
Bound services:{}                     ← 空的,没绑上
Enabled services:{...PageWatcher}     ← 但设置说是开的
Binding services:{...PageWatcher}     ← 卡在"正在绑定"
```

**结果**:`sConnected` 一直是 false,App 完全不推页面。

### 触发条件

**App 进程被杀过之后**(比如切到别的 App 时被 MIUI 清掉),
无障碍服务就容易卡在这个状态。

### 解决办法

| 方法 | 效果 |
|---|---|
| 在设置里**关掉再打开** | ⚠️ 不一定成功(我试了没恢复) |
| **重启手机** | ✅ **实测有效**,重启后立刻正常绑定 |

### 建议

1. **把这个 App 加入 MIUI 的后台白名单 / 锁定任务**,别让它被杀
2. 如果发现悬浮窗的 `🔍` 行不更新了,先看设置里显示的是"已开启"还是卡住,
   实在不行**重启手机**
