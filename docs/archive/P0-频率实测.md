# P0:频率下界实测报告

**测试日期**: 2026-10-02
**硬件**: ESP32-S3-N8R8 + BLE HID (NimBLE/HOGP)
**手机**: Samsung SM-S918U1 / Android 16 / 1080×2316

## 一、固件侧相关参数

| 参数 | 值 | 位置 |
|---|---|---|
| `REPORT_THROTTLE_MS` | **4 ms** | `hid_touch.h`(每帧后固定延迟) |
| BLE 连接间隔请求 | **7.5 ~ 15 ms** | `hid_transport_ble.cpp`(`updateConnParams(6, 12, 0, 400)`) |
| 流控超时 | 40 ms | `HidTouch::sync()` 等 `readyToSend()` |

## 二、实测数据(板子自报耗时)

| 步数 | 耗时 | 每步 |
|---:|---:|---:|
| 1 | 48 ms | 48.0 ms |
| 2 | 96 ms | 48.0 ms |
| 5 | 240 ms | 48.0 ms |
| 10 | 480 ms | 48.0 ms |
| 20 | 960 ms | 48.0 ms |
| 40 | 1536 ms | **38.4 ms** |

> 每步内容:`T x y 20`(点击,按下持续 20ms)

**线性拟合**:固定开销 ≈ **9.8 ms**,每步 ≈ **38.2 ms**

**验证**:把点击时长从 20ms 降到 1ms,50 步耗时 928ms → **18.6 ms/步**。

→ 结论:**每步的 BLE 往返开销约 18ms,与点击时长无关**。

## 三、内核侧实测(相邻报文间隔)

用 `getevent` 抓 `ABS_MT_POSITION_X` 事件的时间戳:

| 轮次 | 最小间隔 |
|---|---|
| 第 1 轮 | 11.1 ms |
| 第 2 轮 | 12.4 ms |

→ 与 BLE 连接间隔 7.5~15ms 吻合。**这是物理下界,无法突破。**

## 四、结论与设计取值

| 项 | 取值 | 依据 |
|---|---|---|
| **频率下限** | **10 ms** | 接近 BLE 物理下界 11ms,再小无意义 |
| **频率默认值** | **100 ms** | 兼顾"别太快"和"够用" |
| 频率语义 | **两次执行之间的最小间隔** | 若流程自身耗时 > 频率,则连续执行不报错 |
| 最快可达速率 | 约 **20 ~ 90 次/秒** | 取决于步骤内容 |

### UI 必须说明的两点

1. **频率 ≠ 执行速度**:频率只是"最小间隔"。若流程本身要 500ms,
   设 50ms 也只会每 500ms 跑一次(连续执行),不会加速。
2. **流程耗时要在 UI 上展示**(来自板子 `run.elapsedMs`),
   用户才能判断频率设多少合理。

## 五、对实现的影响

- 板子侧 `/api/schedule` 的参数需从**秒**改为**毫秒**(`intervalSec` → `intervalMs`)
- 网页控制台与 App 的文案都要从「定时」改为「频率」
- 校验:频率 < 5ms 时钳制到 10ms,并提示
