# 事故:注入点击差点清空所有流程

**时间**:2026-10-05 23:33
**严重度**:**差一次点击就全没了**(已拦下)
**结果**:流程完好,并修掉了根因 + 加了两道保险

---

## 怎么发生的

我在验证「频率运行状态显示」时,用 API 启动了频率循环:

```
POST /api/schedule?index=4&ms=1500&dur=60
→ 已开始频率执行:每 1500 毫秒一次,连续 60 秒后自动停
```

**但当时前台是我们自己的 App,不是大麦。**

而这个流程 `大麦通用版本` 的坐标是给它在大麦上用的:

```
T 0.632 0.917 30 立即预定      → 在我们 App 上 = (682, 1861)
T 0.757 0.914 30              → 在我们 App 上 = (817, 1855)
```

**这两个坐标在我们 App 的「维护」区** —— 正好是「清空所有流程」那些按钮。

几十秒后我发现屏幕上弹着:

```
确定清空板子上所有流程?(重启后会写回示例)
                              [取消]  [确定]
```

**立刻点了「取消」。** 流程 5 个全在。

---

## 根因:遮罩在频率循环期间会「闪」

执行时本来有一层遮罩(`buildBusyMask`)吃掉触摸,由 `run.running` 驱动:

```java
// setRunning()
busyMask.setVisibility(run ? VISIBLE : GONE);
```

**问题**:频率循环是「执行 → 等间隔 → 再执行」。
`run.running` 只在每次执行的那 ~233ms 里是 true,
**间隔期间是 false** → 遮罩一闪一闪。

而注入的点击是**绝对坐标、系统级**的 ——
落在遮罩隐藏的那段时间里,就直接打到下面的按钮上了。

`canTap()` 也一样:

```java
private boolean canTap() {
    if (running) return false;      // ← 只看 running
    ...
}
```

## 修了什么

### ① 遮罩和按钮锁改为「板子在忙」驱动

```java
// uiTick(每秒)
if (busyMask != null) {
    boolean cover = running || boardBusy;      // boardBusy = 跑流程 或 频率循环
    busyMask.setVisibility(cover ? VISIBLE : GONE);
}

private boolean canTap() {
    if (running || boardBusy) return false;    // ← 补上 boardBusy
    ...
}
```

`boardBusy` 来自板子状态里的 `run.running` **或** `sched.active` ✅

### ② 启动频率时「立刻」上锁

状态轮询是 2 秒一次,那 2 秒内还有窗口。所以在点「开始」的瞬间就锁:

```java
boardBusy = true;
if (busyMask != null) busyMask.setVisibility(View.VISIBLE);
board.schedule(idx, ms[0], durMs, cb);
// 失败则解锁
```

### ③ 「清空所有流程」改成两步确认

这是**不可撤销**的破坏性操作,按钮位置又正好在流程容易点到的坐标上。

**第二步要求手输「清空」两个字**:

```
第一步: ⚠️ 清空所有流程
        这会删掉板子上全部流程,板子自带的功能无法撤销。
        (服务器上有完整备份,可以恢复 —— 但还是别误触。)
        确定要继续吗?                    [取消] [继续]
                    ↓
第二步: 真的要清空的话,请在下面输入「清空」两个字:
        [_______________]
        输入不对就什么都不会发生。        [取消] [确认清空]
```

**注入的短按点击不可能完成「输入文字」** —— 这是关键。

## 教训

### 1. 跑流程前必须确认目标 App 在前台

这是我犯的错 —— 直接用 API 起了循环,没管前台是什么。
**坐标是绝对的,前台不对就会点到别的地方。**

以后验证流程,要么:
- 先用 `monkey` 把目标 App 拉到前台
- 要么建**专用的测试流程**,坐标故意放在安全区域

### 2. 破坏性操作必须「物理上难以误触」

单次确认框挡不住注入点击 —— 因为注入点击**连确认框的按钮也能点**。
有效的办法只有:
- **要求输入文字**(注入点击做不到)
- **长按**(注入是短按)
- 或者把按钮挪到流程不会碰到的位置

### 3. 遮罩不能绑在「瞬时状态」上

`running` 是**瞬时**的,频率循环有间隙。
凡是"执行期间要挡住"的逻辑,都要用**整个繁忙周期**,不是单次执行。

### 4. 备份不是可选项

这次万幸。
**在真的出事之前**把备份做好(心跳上报内容),成本很低,价值极高。
