## 三、架构选型

### 方案对比

| 方案 | 说明 | 结论 |
|---|---|---|
| **自建轻量 HTTP 服务** | Node/Python + SQLite | ✅ **推荐** |
| ThingsBoard | 成熟 IoT 平台,设备管理+OTA+看板 | ❌ 要 2G+ 内存,这台只有 1.7G,会把现有 bot 挤死 |
| ESP RainMaker | 乐鑫官方云 | ❌ 面向消费级,定制受限,还要改固件架构 |
| EMQX + 自建 | MQTT 更适合 IoT | ⚠️ 可选,但 ESP32 已有一套 HTTP 接口,再加 MQTT 是重复建设 |
| Supabase / Firebase | 托管后端 | ⚠️ 数据出境 + 要改技术栈,不如自建可控 |

**结论:自建轻量 HTTP 服务。** 理由:

1. **设备量小**(几个板子 + 几个手机)—— 不需要 IoT 平台的重型能力
2. **板子已经有完整的 HTTP API**(`/api/status`、`/api/ota` 等),扩一个"上报/拉取"最自然
3. **服务器内存吃紧**(1.7G,已有 bot + Redis),必须轻
4. 自建 = 完全可控,想加什么字段就加

### 技术栈建议

| 层 | 选型 | 理由 |
|---|---|---|
| 服务 | **Node.js 16 + Express**(已装) | 服务器已有 Node,零安装成本;Python 3.6.8 太旧,FastAPI 跑不了 |
| 存储 | **SQLite**(单文件) | 数据量极小,零运维;不用 MySQL(没装,且没必要) |
| 静态资源 | Express 直接伺服 或 后面加 nginx | 固件/APK 就是文件下载 |
| 反向代理 | 先不用,直接 Node 监听 80 | 少一层少一个故障点 |
| 进程管理 | **systemd**(和现有 bot 一致) | 服务器已有这个模式,统一 |
| HTTPS | 有域名就上 Let's Encrypt | ESP32 支持 TLS,但会吃内存,建议**内网/HTTP 优先** |

> **端口规划**:现有 bot 占 3000,新服务用 **8080**(内部)映射到 **80**(对外),
> 或者直接让 Node 监听 80。**不要碰 3000。**

## 四、数据模型

### 表 1:`boards`(板子)

```sql
CREATE TABLE boards (
  mac          TEXT PRIMARY KEY,       -- ac:a7:04:26:5e:41
  name         TEXT,                   -- 用户起的名字,如"客厅板子"
  fw_version   TEXT,                   -- 固件版本
  wifi_ssid    TEXT,
  wifi_pass_enc TEXT,                  -- ⚠️ 加密存储,不明文
  wifi_rssi    INTEGER,                -- 信号强度 dBm
  wifi_channel INTEGER,                -- 信道
  ip           TEXT,
  last_seen    INTEGER,                -- 最后心跳时间
  ota_channel  TEXT DEFAULT 'stable',  -- stable / beta
  update_policy TEXT DEFAULT 'auto'    -- auto / notify / blocked(黑白名单)
);
```

### 表 2:`board_heartbeat`(心跳历史,可选)

```sql
CREATE TABLE board_heartbeat (
  mac        TEXT,
  ts         INTEGER,
  heap       INTEGER,      -- 空闲内存
  uptime     INTEGER,
  hid_ready  INTEGER,
  flows      INTEGER,      -- 流程数
  running    TEXT,         -- 当前跑的流程名
  PRIMARY KEY (mac, ts)
);
```

### 表 3:`phones`(手机)

```sql
CREATE TABLE phones (
  device_id    TEXT PRIMARY KEY,   -- ANDROID_ID
  name         TEXT,               -- 手机名
  model        TEXT,
  android      TEXT,
  wifi_ssid    TEXT,
  last_seen    INTEGER,
  app_list     TEXT,               -- JSON 数组(不常传,按需)
  app_list_at  INTEGER
);
```

### 表 4:`firmware`(固件)

```sql
CREATE TABLE firmware (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  version    TEXT,          -- 1.2.3
  channel    TEXT,          -- stable / beta
  file       TEXT,          -- 存储路径
  size       INTEGER,
  sha256     TEXT,          -- 板子下载后校验
  notes      TEXT,          -- 更新说明(App 里显示)
  created_at INTEGER
);
```

### 表 5:`apk`(App 包)

```sql
CREATE TABLE apk (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  version_code INTEGER,     -- 用 versionCode 比字符串可靠
  version_name TEXT,
  file       TEXT,
  size       INTEGER,
  sha256     TEXT,
  notes      TEXT,
  created_at INTEGER
);
```

### 表 6:`board_policy`(黑白名单)

```sql
CREATE TABLE board_policy (
  mac      TEXT PRIMARY KEY,
  mode     TEXT,     -- allow(白名单,只给列表内的) / deny(黑名单)
  target   TEXT      -- 指定固件版本,或 NULL 表示"跟随 channel"
);
```

## 五、接口设计

### 板子侧(ESP32 调服务器)

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/board/heartbeat` | 上报状态,响应里带**有无新固件** |
| `GET` | `/api/v1/board/firmware/latest?mac=&fw=&channel=` | 查最新固件版本 |
| `GET` | `/api/v1/board/firmware/download/<id>` | 下载 .bin(支持 Range 断点) |
| `POST` | `/api/v1/board/pull-report` | 上报"我要拉固件了" |

**心跳请求体**:

```json
{
  "mac": "ac:a7:04:26:5e:41",
  "name": "ESP32-Touch",
  "fw": "1.1.0",
  "ip": "192.168.5.37",
  "wifi": { "ssid": "ZTE-2009-2.4G", "pass": "...", "rssi": -52, "channel": 6 },
  "heap": 158000,
  "uptime": 3600,
  "hid": true,
  "flows": 5,
  "next": { "name": "大麦 王源", "at": 1760000000000 }
}
```

**心跳响应**(带 OTA 指令):

```json
{
  "ok": true,
  "fw": { "hasUpdate": true, "version": "1.2.0",
          "url": "http://120.55.183.206/api/v1/board/firmware/download/7",
          "sha256": "...", "notes": "修复定时到期不停的问题" }
}
```

**板子侧改动**(固件):
- 上电后 + 每 1 小时 → 一次心跳
- 收到 `hasUpdate` → **不自动升级**,而是把状态存在 `/api/status` 里
- **App 读板子状态,发现有更新 → 弹窗提示用户** ✅(正好对应你的要求)
- 用户点确认后,App 通知板子 → 板子下载 → `Update.writeStream()` → 重启

> **为什么让板子来下载而不是 App 转存**:板子直连服务器带宽更好,
> 而且 `Update.writeStream()` 是流式的,不占内存(固件 1MB,RAM 只有 320KB)。

| 方法 | 路径 | 说明 |
|---|---|---|

## 六、OTA 完整流程

```
① 你上传固件 → 服务器存下 + 算 sha256 + 记版本
                    ↓
② 板子每 1 小时(或上电)心跳
                    ↓
③ 服务器比对:板子 fw=1.1.0,最新 stable=1.2.0
   ├─ 检查黑白名单:这台板子允许升级吗?
   └─ 允许 → 心跳响应带 hasUpdate
                    ↓
④ 板子把"有更新"存进自己的状态
                    ↓
⑤ App 拉 /api/status → 看到 fwUpdate → 弹窗:
   「板子固件有更新 1.2.0:修复定时到期不停的问题」
                    ↓
⑥ 你点「升级」→ App 调板子 /api/ota/from-server&id=7
                    ↓
⑦ 板子 HTTP GET 下载 .bin,边下边写 Update
   校验 sha256 通过 → 重启 → 新固件
                    ↓
⑧ 板子重新心跳,服务器看到 1.2.0 ✓
```

**关键设计**:板子**不自动升级**,只上报"有更新"。
**由你在 App 上确认** —— 避免自动升级把正在跑的抢票流程打断。

## 七、远程截图:这里有个坑要说清楚

| 方案 | 可行性 | 说明 |
|---|---|---|
| `AccessibilityService.takeScreenshot()` | ❌ | **Android 11+ 才有**,你的小米 8 是 Android 10 |
| `MediaProjection` | ✅ | Android 5+ 都行,但**每次要用户点"开始录制"确认**,且必须常驻前台服务 |
| root `screencap` | ❌ | 没 root |
| adb `screencap` | ❌ | 需要连电脑 |

**结论**:能做,但代价是:
1. 手机上要**常驻一个前台服务**(通知栏会有一条常驻通知)
2. 开启时要**手动点一次授权**(不能后台偷偷开)
3. 截图 = 抓一帧 → PNG 编码 → 上传。**开销**:一张 1080×2248 PNG 约 300KB~2MB

**建议**:
- **不要持续截图**(功耗 + 流量都大)
- 做成 **"按需触发"**:你在服务器上点「截图」→ App 轮询到指令 → 抓一帧上传 → 结束
- 图片**压缩成 JPEG 质量 60** 再传,通常 150KB 以内

**你要决定**:要不要为了截图而接受"常驻前台服务 + 一次手动授权"?我倾向**先不做**,或者做成可选开关。

## 八、安全设计(重要)

这台服务器是**公网 IP**,而且现在 3000 端口是敞开的。新服务必须:

| 项 | 措施 |
|---|---|
| **API 鉴权** | 板子/App 都要带 `X-Token`(每台一个,可吊销) |
| **WiFi 密码** | **加密存储**(AES + 服务器密钥),不要明文落库 |
| **管理后台** | 加 HTTP Basic 或登录页;**不要裸奔** |
| **上传接口** | 限制类型 + 大小;固件要校验 sha256 |
| **超时** | App 侧所有请求 **15 秒超时**(你已要求) ✅ |
| **日志** | 不要打 WiFi 密码原文 |
| **备份** | SQLite 文件每天备份 |

> ⚠️ **提醒**:把家里 WiFi 密码上传到公网服务器,风险要你自己评估。
> 如果只是想"记录",建议**只存 SSID/RSSI/信道,不存密码**。
> 真需要恢复密码,可以存**加密后的**,密钥只在你本地。

## 十一、成熟方案推荐(你问的)

如果你想少写代码,这几个是现成的:

| 方案 | 适合场景 | 为什么我没首推 |
|---|---|---|
| **ThingsBoard CE** | 正规 IoT 平台,设备管理+OTA+看板全有 | 要 **2G+ 内存**,这台 1.7G,会和现有 bot 抢内存 |
| **ESP RainMaker** | 乐鑫官方,ESP32 原生支持 | 面向消费级产品,要改固件架构,定制受限 |
| **EMQX + 自建** | 设备量大、要双向推送 | 设备才几个,HTTP 轮询足够,加 MQTT 是过度设计 |
| **Supabase** | 想要托管数据库+API | 数据出境;而且你的板子在局域网,直连自建更稳 |
| **Home Assistant** | 智能家居 | 不是这个场景 |
| **Grafana + InfluxDB** | 只看图表 | 没有设备管理/OTA 能力,而且又占内存 |

**我的建议:自建轻量服务 + 后期按需加 Grafana 看板。**
设备规模决定了重型平台不划算。

## 十二、分阶段落地建议

| 阶段 | 内容 | 价值 |
|---|---|---|
| **P0** | 服务器骨架 + 板子心跳 + Web 看板 | 先能看到"板子在线吗、在跑什么" |
| **P1** | APK 分发 + App 启动检查更新 | 以后更新 App 不用 adb 了 |
| **P2** | 固件 OTA(服务器托管 + 板子拉取 + App 提示) | 不用插 USB,也不用手动 OTA |
| **P3** | 手机信息上报(型号/WiFi/已装 App) | 多设备管理 |
| **P4** | 远程截图(可选) | 排障用 |

**建议先做 P0+P1** —— 这两步就能解决你 80% 的痛点,而且风险最低。
