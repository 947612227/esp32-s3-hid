## 先说那个"乱"的来源:现在是**三处真相**

你感觉乱是对的 ✅ 根因在这一条:**「流程」到底谁说了算,现在有三个地方**

```
① 板子的 LittleFS(spiffs)   ← 流程的**正文**(tap/swipe/wait 那些指令)
       ▲ 板子→服务器**单向**备份
② 服务器的 board_flows 表    ← 只是**只读快照**,服务器**从不回写**给板子
       ▲ App→服务器**单向**上报
③ App 的 SharedPreferences   ← 只存**状态**(启用/定时/频率/绑定哪个App/重复次数)
```

**关键事实(我逐个查过)**:

| 数据 | 权威来源 | 服务器角色 |
|---|---|---|
| 流程**正文** | **板子的 spiffs** | 只存备份(`board_flows`),13 行,单向收 |
| 流程**状态**(启用/定时/频率) | **App 的 SharedPreferences** | 只存备份(`schedules`),单向收 |
| 流程的**名字列表** | 板子 | 备份 |

**⇒ 服务器现在是"只读的观察者",不是"管理者"** ✅
你要的「服务器存、App 下载」= 要把这个方向**反过来**,这是这次最大的改动 ✅

### ④ 状态灯语义 + 运行中禁点灯 ❌ 未实现

**你要的**:
```
待机 → 红色
运行中 → 黄色
执行结束 → 绿色
闲置 → 灭灯
运行中禁止服务器远程点灯
```

**现在的**:
```cpp

case 2:  执行中 → 暗黄(18,14,0)
default: 未连接 → 暗蓝(0,0,14)
```

**差异**:
| | 你要 | 现在 |
|---|---|---|
| 待机 | 🔴 红 | 🔵 暗蓝 |
| 运行 | 🟡 黄 | 🟡 暗黄 ✅ 一致 |
| 结束 | 🟢 绿 | ❌ 没有"结束"这个状态 |
| 闲置 | ⚫ 灭 | ❌ 不灭(一直亮) |
| 运行中禁点灯 | 要 | ❌ **完全没做** |

**我查过**:`led.cpp` 和 `ble_command.cpp` 里 **`running` 出现 0 次** ✅
`/api/led` 的处理器里也没有任何运行状态判断 ✅
**⇒ 现在流程跑着的时候,后台/App 照样能改灯** ✅

**推荐方案**:
1. 固件加一个"结束"状态(流程跑完后亮绿 3~5 秒,再回待机)✅
2. 板子导出 `Scripts.running()` 类的东西给 LED 判断 ✅
3. 点灯入口加 `if (running) return "运行中,禁止改灯"` —— **三个入口都要加**(串口/HTTP/BLE)✅
4. 语义颜色改成你要的四态 ✅

**工作量:中等**(要动 led.cpp + 三个入口 + main loop 的状态机)
**推荐:做** —— 这个语义更直观,而且"运行中禁点灯"能避免点灯干扰排查 ✅

**建议的中间路线**(性价比最高):

### 这要做的话,必须先定一件事:**流程以谁为准?**

三种可行的架构,我列出优劣:

| 方案 | 谁说了算 | 优点 | 缺点 |
|---|---|---|---|
| **A. 服务器为源** | 服务器 | 群控天然成立 ✅ 换手机/换板子流程都在 ✅ | 板子必须有外网 ⇒ **和 ② 断网运行矛盾** ⚠️ |
| **B. 板子为源** | 板子 | 断网天然成立 ✅ 现在就是这样 ✅ | 群控难 ✅ 服务器只是备份 ✅ |
| **C. 服务器为源 + 本地缓存**(**推荐**) | 服务器,但离线可用 | **两个都要** ✅ | 要做**冲突合并**,最复杂 |

**推荐 C**,具体形态:

```
① 服务器存流程(权威)+ 每条流程带 version / updatedAt / 来源标记
② App 启动 / 定时:拉服务器的流程列表 + 版本号
③ 和本地(板子上的 + App 的状态)比对:
     · 服务器新 → 下载并写入板子
     · 本地新   → 上传到服务器
     · 都改了   → 冲突:按 updatedAt 或问用户
④ 断网时:完全用本地,正常跑;联网后同步
```

**⚠️ 要提前想清楚的三个坑**:

1. **流程正文在板子上,状态在 App 上 —— 拆两处是现在的设计** ✅
   统一管理要么**把状态也搬到服务器**(App 变纯客户端 ✅),要么**两边都同步** ✅
   **推荐前者**:状态(启用/定时/频率)也进服务器 ✅ —— 否则"服务器为源"不成立 ✅
2. **冲突合并是真难点** ✅
   两台手机同时改同一条流程怎么办?✅
   **推荐:先不做自动合并**,用"最后写入者赢 + 保留历史版本" ✅
   (服务器已经有 `flow_history` 表,就是干这个的 ✅)
3. **群控 = 一次推给 N 块板子** ✅
   这要求板子都能连服务器 ✅ ⇒ 回到"板子必须有外网" ✅
   如果做不到(比如你现在这块),**群控只能靠 App 中转**(App 连着多块板子?—— 一块手机通常只连一块 ✅)
   **⇒ 群控的实际前提是:板子能上外网** ✅ 这一点建议你先确认 ✅

**工作量:大**(服务器 3~4 个接口 + 版本比对 + App 同步逻辑 + 冲突策略 + 后台流程管理页)
**建议**:分两步 —— 先做「**App 启动拉服务器的流程快照**」(只读,不做冲突)✅
跑通了再加双向同步 ✅

| 3 | **App 没有服务器连接状态展示**,所有服务器调用静默失败 | 用户不知道云端通没通 | 🟡 中 |
| 4 | **运行中不禁止点灯** | 点灯会干扰排查;而且"结束绿"没有 | 🟡 中 |
| 5 | **App 无任何鉴权**,`/api/v1/app/*` 靠一个固定 token | 谁装了 App 都能上报 ✅(目前是内网自用,风险可控) | 🟡 中 |
| 6 | **后台 `needAdminRole` 只在部分接口**,审计里的 `led`/`upload_apk` 权限我看是 admin ✅ 但注册登录上线后要重新梳理 ✅ | 以后多用户会出问题 | 🟡 中 |
| 7 | **服务器上只有一次手工备份**(10-05),没有 git、没有定时备份 | 出事就丢 | 🔴 高 |
| 8 | **板子固件版本号是硬编码 `1.2.0`**,OTA 靠版本比对 | 群控时要靠它判断一致性,得改 | 🟢 低 |
| 9 | **板子 `/api/ota/from-server` 依赖板子能连服务器** ⇒ 你现在的板子用不了 | 远程升级对这块板子失效 | 🟡 中 |
| 10 | 后台配色名不副实(是蓝点缀不是绿黑) | 观感 | 🟢 低 |

## 推荐的处理顺序

按"性价比 × 依赖关系"排:

| 顺序 | 做什么 | 工作量 | 为什么先做 |
|---|---|---|---|
| **1** | **代码备份上服务器**(git + 定时备份) | 小 | 后面所有改动的前提,出事能回滚 |
| **2** | 设备管理页拆出来(第 ⑩ 条) | 小 | 顺手,结构已经支持 |
| **3** | App 加「服务器连接状态」(第 ③ 条) | 小 | 用户能看见问题,后续排查都靠它 |
| **4** | 状态灯四态 + 运行中禁点灯(第 ④ 条) | 中 | 独立,不牵扯架构 |
| **5** | **流程管理架构定型**(新增诉求) | 大 | **必须先定"谁为源"**,否则后面全是返工 |
| **6** | App 注册登录 + 服务器审核(第 ⑤ 条) | 中偏大 | 依赖第 5 条的用户概念定型 |
| **7** | 后台美化 / 是否上 Vue(第 ⑨⑪ 条) | 中 | 最后做,前面结构稳了再美化 |

**我的整体建议**:先做 **1~4**(一天内),把地基和可见性补齐 ✅
然后**花时间把第 5 条的架构想清楚**(这个决定影响最大),再做 6~7 ✅
