# 连了板子的热点,还能同步数据吗?

## 直接回答:**一半能,一半不能 —— 但补上了**

| 上报 | 谁发 | 走哪条路 | 板子热点下 |
|---|---|---|---|
| `startupPing` / `reportPhone` / `reportApps` | **App** | 手机互联网(蜂窝) | ✅ 能 |
| `reportSchedules`(带板子 MAC) | **App** | 同上 | ✅ 能 |
| `checkUpdate` | **App** | 同上 | ✅ 能 |
| ~~心跳 / 流程备份 / 在线状态 / 公网IP~~ | ~~板子~~ | 板子的 STA(没网) | ❌ **不能** |

**关键**:Android 连上"无互联网的 WiFi"时,默认**保留蜂窝数据**用于上网 ✅
所以**手机到服务器是通的**,但**板子到服务器不通**。

---

# 为什么这是个问题

板子自己发不了心跳,意味着云端丢掉这些:

| 丢什么 | 后果 |
|---|---|
| 在线状态 | 看板一直显示 🔴 离线(其实是好的) |
| 公网 IP / 位置 | 看不到板子在哪 |
| **流程备份** | ⚠️ **误删流程就找不回来了** —— 这是之前踩过坑专门加的保险 |

**最后一条最要命。** 之前误删过流程,靠服务器留底救回来的 ✅

# 补法:**让 App 代板子上报**

```
板子(只有热点,无外网)
   ↑ HTTP(局域网)
手机 App ──→ 服务器(走蜂窝)          ← 中转
```

## 服务端

新增 `POST /api/v1/app/board-relay`,把 App 报上来的板子状态
**灌进和板子心跳完全一样的处理逻辑** ✅

为此把心跳的核心逻辑抽成了公共函数:

```js
// 原来:心跳 handler 里一大坨
// 现在:
async function applyBoardReport(b, mac, pubIp, doGeo) { ... }

app.post('/api/v1/board/heartbeat', needBoard, async (req, res) => {
  const pubIp = clientIp(req)...          // 源地址 = 真实公网 IP
  const fw = await applyBoardReport(b, mac, pubIp, true);
  json(res, 200, { ok: true, firmware: fw || { hasUpdate: false } });
});

app.post('/api/v1/app/board-relay', needApp, async (req, res) => {
  // ⚠️ pubIp 留空、doGeo=false ——
  //    手机的公网 IP 不等于板子的,传上去会把手机位置错记到板子头上
  await applyBoardReport(b, mac, '', false);
  json(res, 200, { ok: true });
});
```

## App 端

`uiTick`(1 秒节拍)里挂了一个 30 分钟一次的代报:

```java
private void maybeRelayBoard() {
    if (relaying) return;
    if (now - lastRelayAt < 30 * 60 * 1000L) return;   // 30 分钟一次
    ...
    // ① 读板子 /api/status
    // ② 先报一份"只有状态"的(读流程失败也不至于什么都没有)
    // ③ 再逐个读流程内容(一次一个请求 —— 板子 WebServer 是单线程的)
    // ④ 全读到了再报一次(带流程备份)
}
```

**为什么先报一次再补一次**:读 6~16 个流程要好几个请求,
中间任何一个失败都要保证"状态"已经上去了 ✅

**为什么串行读流程**:板子的 WebServer 是单线程的,并发压它会拖慢 ✅

# 局限(要知道)

| 项 | App 代报能做到吗 |
|---|---|
| 在线状态 | ✅ 能 |
| 流程备份 / 历史 | ✅ 能 |
| 脚本数量、内存、HID 状态 | ✅ 能 |
| **公网 IP** | ❌ **不能** —— 手机的公网 IP ≠ 板子的,故意不上报 |
| **地理位置** | ❌ 同上 |
| **远程固件 OTA** | ❌ 板子下载不了固件 |
| WiFi 配置上报 | ✅ 能(从 status 里带) |

> **想要公网 IP + 位置 + 远程 OTA ⇒ 必须让板子自己有网。**
> 用**手机热点**(方案 B)就能两全 ✅

# 教训

## "设备没网"和"用户没网"是两件事

板子连不上公司网络,但**手机连得上**(蜂窝)。
**中间加一个中转,整个云功能就活了** —— 不用改板子的任何东西 ✅

## 中转时必须想清楚"哪些数据不能代报"

公网 IP / 地理位置是**和网络出口绑定的** ——
手机代报就会把手机的出口位置错记到板子上 ✅
**主动留空,比报一个错的强。**

## 抽函数是为了"两个来源走同一套逻辑"

心跳和代报要写**完全一样**的库 ✅
不抽函数的话,两份逻辑迟早会分叉(改了一边忘了另一边)✅
