# 流程列表与定时任务上报

## 你反馈的问题

> 这块板子的流程没有获取到啊 ac:a7:04:26:5e:40,还有 2 小时 5 分就执行了

查出**两个缺口**,都补了。

---

## 缺口 ①:流程名字没上报

**原因**:板子心跳里只有 `flows: 5` 这个**数量**,没有名字。

**修法**:心跳里加 `flowNames` 数组。

```json
{
  "mac": "AC:A7:04:26:5E:40",
  "flows": 5,
  "flowNames": ["大麦", "大麦 王源 10月11_19:00", "大麦app", "大麦app 三星s23", "大麦小米8"]
}
```

服务端存进新表 `board_flows`(整表替换)。

**实测**:
```
mac: ac:a7:04:26:5e:40  name: ESP32-Touch  fw: 1.0.0  flows: 5

board_flows:
  大麦
  大麦 王源 10月11_19:00
  大麦app
  大麦app 三星s23
  大麦小米8
```

---

## 缺口 ②:下次执行时间没上报(更关键)

**原因**:这是**架构问题**,不是 bug ——

> **定时是存在「手机 App 的本地设置」里的,板子根本不知道。**

板子的 `/api/status` 里那个 `sched` 字段是它自己的**频率循环**(每 N 毫秒重跑),
和 App 里设的"19:30 执行一次"**完全是两码事**。

所以服务端 `next_name` 一直是空的。

**修法**:让 **App 上报**。

```
手机 App  ──POST /api/v1/app/schedule──▶  服务端
  知道自己的定时任务                        存进 schedules 表
  (板子不知道)                              看板显示"下次什么时候执行"
```

### 新增

| 项 | 说明 |
|---|---|
| 表 `schedules` | `board_mac` / `flow_name` / `fire_at` / `mode` / `enabled` / `repeat_count` |
| 接口 `POST /api/v1/app/schedule` | App 上报定时任务(带 boardMac) |
| 板子 `/api/status` 加 `mac` | App 需要它才知道"这是哪块板子" |
| App `Server.reportSchedules()` | **内容变了立刻报,没变每 5 分钟兜底报一次** |

### 实测

```
POST /api/v1/app/schedule 200 9ms

board_mac           flow_name                mode  fire_at              enabled
ac:a7:04:26:5e:40   大麦 王源 10月11_19:00    at    2026-10-05 19:30:00  0
```

看板输出:

```
ESP32-Touch ac:a7:04:26:5e:40
  流程 5 个: 大麦, 大麦 王源 10月11_19:00, 大麦app, 大麦app 三星s23, 大麦小米8
  下次: 大麦 王源 10月11_19:00  10-05 19:30  还有 2时1分  enabled=False
```

---

## ⚠️ 顺手发现一个你可能没注意到的问题

**那个 19:30 的定时,流程是「暂停」状态(`enabled = 0`)—— 到点不会执行!**

我第一版还把暂停的定时**过滤掉了**,结果看板显示"无定时任务" ——
比"有任务但不会跑"更容易误导。

**改成**:暂停的也显示,而且**显眼地标出来**:

```
⏳ 下次:大麦 王源 10月11_19:00 10-05 19:30 还有 2 时 1 分
⚠️ 流程是暂停的,到点不会执行
```

> 如果你希望它到点跑,去 App 里把这个流程改成**开启**状态。

---

## 又踩到的老坑:MIUI 会杀 App

调试时服务端**完全收不到** `/api/v1/app/schedule`,查了半天:

```bash
adb shell ps -A | grep touchpad     # ← 进程不在
```

**MIUI 把 App 进程杀了**(切到桌面就杀),所以它根本没机会上报。

**影响**:

- App 不在运行时,**定时上报/页面推送都不会工作**
- 但**板子的心跳不受影响**(那是板子自己发的)

**建议**:把这个 App 加进 MIUI 的后台白名单 / 锁定任务。

> 这也解释了为什么之前页面识别"时好时坏" —— 不是代码问题,是进程被杀了。

## 现在的完整数据流

```
┌─────────┐  心跳(含 flowNames)  ┌──────────────┐
│  ESP32  │ ────────────────────▶│              │
│  板子    │◀──── hasUpdate ──────│   服务端      │
└─────────┘                      │   MySQL      │
                                 │              │
┌─────────┐  定时上报(含 boardMac)│  boards      │
│ 手机 App │ ────────────────────▶│  board_flows │
│         │  手机信息/已装App/页面 │  schedules   │
└─────────┘                      └──────────────┘
```

**分工很清楚**:

| 数据 | 谁知道 | 谁上报 |
|---|---|---|
| 流程内容、固件版本、WiFi | 板子 | 板子心跳 |
| **定时任务** | **App** | **App 上报** |
| 手机信息、已装 App | App | App 上报 |
| 当前页面 | App(无障碍) | App 推给板子 → 板子转报 |
