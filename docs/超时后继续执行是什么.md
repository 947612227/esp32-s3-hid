# 「超时后继续执行」是什么指令?超时是时间不够吗?

## 你问的

> app 的日志里面有几个超时后继续执行的指令,执行的是什么,
> 超时是等待的时间不够吗?

用你那条真实日志逐行拆开讲。

---

# 〇、先搞清楚:那个 8000 是"最长等待",不是"必须等满"

**`waitfor 支付宝付款 8000` 的意思是:最多等 8 秒,中途发现就立即继续。**

## 代码就是这么写的

```cpp
uint32_t t0 = millis();
uint32_t limit = st.ms ? st.ms : 15000;      // 8000 = 上限
bool ok = false;
while (millis() - t0 < limit) {
    if (pageContains(st.note)) { ok = true; break; }   // ← 一匹配就跳出循环
    idleWait(120);                                     // 每 120ms 检查一次
    if (_stopRequested) break;
}
```

`break` 就是"立刻不循环了" ✅ —— 所以匹配到的那一刻(worst case 120ms 后)就往下走。

## 实测

同一台板子,同一个流程里放两个 waitfor:

```
[2/5] 等待页面:ProjectDetail
  → 页面已出现(等了 0 ms)          ← 存在的词,秒过
[4/5] 等待页面:绝不存在的词zzz
  → 超时(等了 8062 ms)             ← 不存在的词,才等满

完成:5 步,耗时 8153 ms              ← 0 + 8 秒,完全对得上
```

## 你自己流程里的日志也是这个规律

```
[4/11] 等待页面:抢票预约  → 页面已出现(等了 1634 ms)    ← 限时 3000,只等了 1.6 秒
[10/11] 等待页面:可预约   → 页面已出现(等了 1934 ms)    ← 限时 3000,只等了 1.9 秒
```

**限时 3 秒,实际 1.6 / 1.9 秒就走了** —— 说明它一直在轮询,发现就走 ✅

## 两种结果

| 情况 | 日志 | 下一步 |
|---|---|---|
| **8 秒内出现** | `→ 页面已出现(等了 N ms)` | **立即执行下一步** ✅ |
| **8 秒内没出现** | `→ 超时(等了 8000 ms)` | **也执行下一步**(不报错、不中断) |

> ⚠️ 关键点:**两种情况下都会往下走**。
> 所以 `waitfor` 之后如果跟着一个点击,那个点击**不管等没等到都会执行**。
> 要在"没等到就不点"的时候加 `ifpage`;要在"等到了就停止循环"的时候加 `break`。

## 分辨率:每 120 毫秒查一次

轮询间隔是 `idleWait(120)`,所以:

| 页面出现的时刻 | 实际继续的时刻 |
|---|---|
| 第 0 ms | 最多 120 ms 后 |
| 第 1000 ms | 最多 1120 ms 后 |

**误差 ≤ 120ms,基本可以忽略** ✅

> 顺带:`idleWait` 在等待期间会让出控制权给网络 ——
> 所以等 8 秒的期间,App 还能正常连板子(不点日志页也能看到悬浮窗日志)。

# 一、「超时后继续执行」的是哪个指令

**只有一个:`waitfor`(等待页面)。**

它的完整行为:

```
waitfor <关键字> <超时ms>
  │
  ├─ 匹配到 → 立刻往下走,日志写「页面已出现(等了 N ms)」
  │
  └─ 超时   → **也往下走**,日志写「超时」
              ⚠️ 它**不执行任何动作**,只是"放行"
```

**所以"超时后继续执行的"不是某个动作,就是 `waitfor` 自己放行。**

---

# 二、为什么设计成"超时不算失败"

因为写脚本的人通常是「**希望**等到」,而不是「**必须**等到」。

| 如果超时就中断 | 现在这样(继续) |
|---|---|
| 页面慢一点 → **整个流程断掉** | 页面慢一点 → 继续走,不影响 |
| 你必须把超时设得很大 | 超时设小点也没关系 |

> **但要注意**:超时继续 ≠ 这一步没作用。
> `waitfor` 的作用是「**别在页面还没到的时候就去点**」。
> 它超时了,说明**后面的点击可能点在错误的页面上** —— 所以要配合 `ifpage` 才稳妥。

---

# 三、超时是"等待时间不够"吗?—— **大多数情况不是**

**新日志会直接告诉你答案。** 现在超时会这样写:

```
[script] [4/6] 等待页面:绝不存在的词xyz
[script]   → 超时(等了 3021 ms 没等到「绝不存在的词xyz」)
[script]     当时页面:com.dsh.touchpad.MainActivity
[script]     那页上的词:触摸注入板 / 12:50:31 / ☰ / 状态 / 流程 / 控制 / 手势 / 日志
[script]     ↑ 从这些词里挑一个(或用悬浮窗 🔍 挑带 ⭐ 的)才能等到;现在这个关键字那页上没有
[script]     超时**不算失败**,下一步照常走
```

**「那页上的词」列表里根本没有你等的那个关键字** ——
那不管把超时调到 1 秒还是 1 小时,**都等不到**。
**这是关键字不对,不是时间不够。**

# 四、三种超时,看日志怎么区分

| 日志里出现 | 真正原因 | 怎么办 |
|---|---|---|
| **有「那页上的词:…」这一行** | **关键字那页上没有** | 从「那页上的词」里挑一个,或用悬浮窗 🔍 挑带 **⭐** 的 |
| **有 `⚠️ 当时没拿到任何页面信息`** | **页面识别没在推**(板子手里是空的) | 检查 App 的「页面识别」是不是 ✅ 已开启;必要时重启手机 |
| **有词,但你知道等一下页面会变** | **确实等太短了** | 把超时 ms 调大(默认 15000) |

> 第二行是**最容易误判**的:看起来像"等太短",实际上是**根本没数据**。
> 以前日志只写「当前页面:(未知)」,看不出区别,所以专门加了这行提示。

# 六、怎么把 waitfor 写对(三步)

```
① 手动走到那个页面(比如"抢票预约"页)
② 点悬浮窗的 🔍 —— 它列出这页所有词
   (在上一页先点一次,这页再点一次,会用 ⭐ 标出本页独有的词)
③ 点那个 ⭐ 词 → 剪贴板里就是能直接用的整行:
      waitfor 抢票预约 8000 等「抢票预约」出现
```

**核心:关键字必须是"那一刻页面上真的有的文字"。**

# 七、更稳的写法:waitfor + ifpage 配对

`waitfor` 超时后照常往下走,所以**后面的点击可能点在错误页面**。
要避免这个,配一个 `ifpage`:

```
waitfor 抢票预约 8000 等抢票预约入口
ifpage 抢票预约
    T 0.639 0.403 30 点抢票预约
else
    wait 1 没进抢票预约页,这次跳过,不乱点
endif
```

这样:
- 到了 → 点 ✅
- 没到 → **不点**,不会乱点到别的地方 ✅

> 你的流程 `[10/11] 等到「可预约」→ [11/11] 点立即预定` 就是这个思路的正确形态。
> 而 `[6/11]` `[8/11]` 那两处,超时后**直接就点了** —— 这是可以改进的地方。
