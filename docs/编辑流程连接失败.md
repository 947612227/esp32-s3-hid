# 点「编辑流程」偶现「连接失败」

## 你反馈的

> 点击编辑时,偶现出现连接失败的情况,避免这种情况

**找到根因了,而且实测是 80% 失败率 —— 不是"偶现"。**

---

## 真凶:流程执行期间板子**完全不应答**

`Scripts.run()` 是**同步阻塞**跑完整个流程的:

```cpp
// main.cpp
void loop() {
  hidTransport().poll();
  netManager().loop();        // ← WebServer 在这里被服务
  netServiceScripts();        // ← 这里面会调 Scripts.run() 把整个流程跑完
  ...
}

// script_engine.cpp
case StepOp::Delay:
  delay(st.ms);               // ← 纯 delay,期间上面那个 loop 完全停转!
```

**流程一跑 → `netManager().loop()` 不再被调用 → WebServer 不处理任何请求。**

这时候在 App 里点「编辑流程」读 `/api/script`,必然超时 → **「连接失败」**。

### 实测数据(A/B)

同一台板子、同一个流程,流程执行期间并发读 `/api/script`:

| | 成功 | 失败 |
|---|---|---|
| **修复前** | 8 | **32(80%)** |
| **修复后** | 40 | **0** |
| 再测一次 | 40 | **0** |

---

## 修法:等待时"让出"控制权

加了一个**空转回调**,脚本等待期间反复调用它:

```cpp
// script_engine.h
typedef void (*IdleHook)();
void setIdleHook(IdleHook h);

// script_engine.cpp
static IdleHook s_idleHook = nullptr;

/** 带服务的等待:等 ms 毫秒,期间不断把控制权让给网络/蓝牙 */
static void idleWait(uint32_t ms) {
  uint32_t t0 = millis();
  while (millis() - t0 < ms) {
    if (s_idleHook) s_idleHook();
    delay(5);
    if (Scripts.stopRequested()) return;   // 等待期间也能被「停止」打断
  }
}
```

`main.cpp` 里接上:

```cpp
setIdleHook([]() {
  netManager().loop();        // 服务 Web 请求
  hidTransport().poll();      // 服务蓝牙
});
```

原来两处裸 `delay()`(`wait` 和 `waitfor` 轮询)全换成 `idleWait()`。

---

## 附带修好的:「停止」快了 250 倍

因为 `idleWait` 里会检查 `stopRequested()`,**等待期间也能被打断**:

```
测试:一个 wait 30000 的流程,3 秒后点停止
修复前 → 要等当前 wait 走完(还剩 27 秒)
修复后 → 0.12 秒就停了 ✅
```

---

## 时序有没有被拖慢?

**几乎没有:**

```
wait 3000 + wait 2000 + wait 1000   →   实际 6010 ms
```

只多了 10ms(5ms 的轮询粒度),可以忽略。

## App 侧也加了三道保险

板子修好是根本,但网络抖动总会有,所以 App 也加固了:

### ① 全局串行化 + 失败重试

板子的 WebServer 是**单线程**的,而 App 里有 **3 个 Board 实例**
(MainActivity / FlowEditActivity / DebugReceiver)各有线程池:

```java
private static final Object NET_LOCK = new Object();   // 同一时刻只允许一个请求
private static final int RETRY = 2;                    // 失败自动重试

for (int attempt = 0; attempt < RETRY && !ok; attempt++) {
    if (attempt > 0) Thread.sleep(180);
    synchronized (NET_LOCK) { ... 发请求 ... }
}
```

### ② 编辑流程时暂停后台轮询

`MainActivity.onPause()` 停掉 `/api/status` 轮询和 `/api/page` 推送,
把带宽让给编辑页。

> ⚠️ **但如果板子正在跑流程就不停** —— `waitfor` 靠的就是页面推送。

### ③ 编辑页自动重试 + 手动重试

- 读失败**自动重试 3 次**(间隔 250/500ms)
- 全失败才提示,并且弹一个带 **「重试」按钮**的对话框 ——
  不用退出去重进
- 编辑页超时从 **6 秒放宽到 12 秒**(板子忙的时候 6 秒不够)

## 教训

### 1. 「偶现」往往不是偶现

用户说"偶现",实测是 **80% 失败** —— 只是触发条件(流程正在跑)不容易被自己意识到。

**别接受"偶现"这个描述,想办法量化它。**

### 2. 同步阻塞的循环会饿死其他子系统

`Scripts.run()` 把整个流程同步跑完,期间的 `delay()` 让 `loop()` 停转。

**凡是"跑很久"的同步逻辑,都要在等待点让出控制权** ——
否则网络、蓝牙、按键全都会没反应。

### 3. A/B 对比是最有力的证据

同一个测试脚本,修复前后各跑一次:
```
修复前:成功 8  失败 32
修复后:成功 40 失败 0
```
**这比任何解释都清楚。**
