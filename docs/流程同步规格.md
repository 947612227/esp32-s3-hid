# 流程同步规格(用户定的,以此为准)

## 一句话

> **服务器是权威存储,永远最新;板子是「服务器上启用那批」的精确副本。**

```
┌─────────────────────────────────────────────────────────┐
│  服务器 —— 流程的权威存储                                    │
│    每个流程有状态:启用 / 禁用 / 删除                          │
└─────────────────────────────────────────────────────────┘
         │                              ▲
   ①首刷 / 点「刷新列表」           ②编辑保存
         ▼                              │
┌─────────────────────────────────────────────────────────┐
│  板子 —— 服务器上「启用」那批的精确副本                       │
│    · 服务器启用的      → 板子上必须有                        │
│    · 服务器禁用/删除的  → 板子上必须没有(直接删掉)             │
└─────────────────────────────────────────────────────────┘
```

## 四个场景

| 场景 | 行为 |
|---|---|
| **板子首次写固件** | 拉服务器上**启用的**流程,写进板子 |
| **板子上编辑后点保存** | **自动同步到服务器** ⇒ 服务器始终最新 |
| **服务器上启用/禁用/删除后,点「刷新列表」** | 板子更新成最新列表:启用全下载,禁用直接删 |
| **服务器上禁用/删除** | 板子上那份**直接删掉** |

## ⚠️ 「刷新列表」的**正确顺序**(关键)

```
① 先"上行":板子上有、服务器没有的 → 上传到服务器
   ↑ **这一步绝对不能省** —— 否则下一步的对齐会把它们当"该删"清掉
② 拉服务器全量(启用 + 禁用/删除的标记)
③ 下行:服务器启用的 → 写进板子
④ 清理:服务器禁用/删除的 → 从板子删掉
```

### 为什么 ① 必须有(血的教训)

我第一版**跳过了 ①** ⇒ 一次刷新时服务器返回 0 条(我测试时把流程都禁用了)
⇒ 对齐逻辑认为"服务器一条都没有" ⇒ **把板子上所有流程全删了**
⇒ 板子上的「向下滚动」被删掉了

**根因**:"服务器没有"有两种可能 ——
- 服务器上真的被禁用/删除了 ⇒ 该清
- 板子上独有的(用户刚建的 / 服务器数据缺失)⇒ **该上传,不该删**

**⇒ 只有先做 ① 把板子独有的传上去,②之后的对齐才是安全的** ✅

## 实现要点

### 服务器侧

```sql
-- flows 表
owner, name, text, meta, ver, deleted,
status ENUM('enabled','disabled','deleted') DEFAULT 'enabled'
```

- **全量拉取**:`WHERE owner = ?` —— **禁用/删除的也返回**(作标记,`text=null`)
  这样客户端才能**精确知道**该删哪几条
- **增量拉取**:`WHERE owner = ? AND ver > ?`
- 每次改动 **ver +1**(owner 内单调递增)

### App 侧(FlowSync)

```
fullSync():
  ① board.scripts() 拿板子上的名字
  ② 逐个 board.scriptText(i) 拿正文
  ③ 拉一次服务器清单(名字 + ver)
  ④ 板子有、清单没有  → Server.pushFlow(baseVer=0)
  ⑤ 清单有、板子没有  → board.save()(只对 enabled)
  ⑥ 服务器 disabled/deleted → board.delete()
```

### 安全闸(必须保留)

- **服务器返回空列表时,绝不做删除对齐** —— 分不清"真空"还是"接口异常"
- **只删服务器明确标了 disabled/deleted 的**,不删"没出现在列表里"的

# ⚠️ 实现时踩的坑(两个都是我自己造的)

## 坑 ① `refreshing` 标志泄漏 ⇒ 「刷新列表」按钮"不生效"

```java
if (force) {
    if (refreshing) { cb.done(false, "正在刷新中,请稍候"); return; }
    refreshing = true;
}
```

但**失败分支直接 return 了,没把 refreshing 清掉** ✅
⇒ 下一次点刷新被防抖挡掉 ⇒ 日志:`服务器拉取失败:正在刷新中,请稍候`
⇒ 用户看到的就是"**刷新列表按钮似乎不生效**" ✅

**修**:所有出口(失败 / 解析异常 / 完成)都要清 ✅

## 坑 ② 「服务器零条启用」时仍然对齐 ⇒ **又差点清空板子**

第一次加固只判断了 `serverDisabled 非空` ✅
但**服务器把 10 条全标成 disabled 时**,`serverDisabled` 恰好是 10 条 ✅
⇒ 还是有内容 ⇒ 加固没拦住 ⇒ **又删了 10 条**(这次 BLE 删除失败,侥幸没删成)

**修**:加一条更强的判断 ——

```java
final boolean serverHasNoEnabled = serverEnabled.isEmpty();
if (serverHasNoEnabled && !serverDisabled.isEmpty()) {
    Log.w("TouchPad", "服务器启用列表为空,判定为异常,跳过对齐清理");
}
if (forceAlign && !serverDisabled.isEmpty() && !serverHasNoEnabled) { ... }
```

**依据**:正常使用时服务器上**总会有几条是启用的** ✅
**"一条启用都没有"几乎一定是数据异常**(被批量改状态 / 换设备 / 数据损坏)
⇒ 那时**宁可什么都不删** ✅

> **两次都栽在同一个地方:把"服务器返回的异常状态"当成"用户意图"。**
> 删除类操作,遇到**全空 / 全禁用**这种"边界极值",应该**停下来问人**,
> 而不是照做 ✅
