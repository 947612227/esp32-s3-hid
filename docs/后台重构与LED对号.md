# 后台重构(左侧菜单多页面)+ LED 对号

## 一、修掉的三个「数据看不见」

| 现象 | 根因 | 修法 |
|---|---|---|
| **最后上报时间 `NaN 天前`** | `/api/admin/phones` 把 MySQL 的 DATETIME **原样**给前端(JSON 化后是 ISO 字符串),前端 `Date.now() - ms` 算出 NaN | 后端统一转**毫秒数**;前端 `ago()` 再加一道 `toMs()` 保险 |
| **APP 管理上传时间是个横杠** | 前端读 `a.createdAt`,后端 `SELECT *` 给的是 `created_at` | 后端做字段名映射(snake_case → camelCase)+ 时间转毫秒 |
| **板子一直显示离线 / 手机没状态** | App 的「代板子上报」里 `relaying` **卡死**了 | 加**中继看门狗**(超 3 分钟强制复位) |

### 关于「板子显示离线」的完整解释

板子在内网,**服务端够不到它**,只能等它来心跳 ✅
但这块板子连不上公司网(飞连认证)⇒ 它发不出心跳 ⇒ 服务端确实认为它离线 ✅
**补救是 App 代报** —— App 有手机流量,把板子状态中转上来 ✅
而那个中转的 `relaying` 标志一卡就永远不再报 ✅ → 所以看板上一直离线 ✅

```java
// 修前:只有"流程全读完了"才复位
if (k >= idxs.length()) { ...; relaying = false; }
//        ↑ 任何一次回调不来(蓝牙超时/队列卡)就永远是 true

// 修后:开头先看看是不是卡太久
if (relaying) {
    if (now - relayStartedAt < 3 * 60 * 1000L) return;
    boardLog("上次中继卡住超时,放弃并允许重试");
    relaying = false;
}
```

## 三、LED 对号功能

### 问题

几块板子都叫 `ESP32-Touch` / `ESP32S3 Touch HID` ✅
后台列表里分不清谁是谁 ✅ 只能对 MAC 地址,很麻烦 ✅

### 做法:让板子的灯亮起来 ✅

**硬件**:ESP32-S3 开发板板载 **WS2812 RGB 灯,GPIO48**
(Arduino 框架里就是 `PIN_NEOPIXEL 48`)✅

**三种点灯方式:**

| 谁 | 怎么点 | 多久生效 |
|---|---|---|
| **串口** | `LED 255 0 0 2000` / `BLINK` | 立刻 |
| **HTTP** | `GET /api/led` 或 `?r=&g=&b=&ms=` | 立刻 |
| **蓝牙控制通道** | `LED` / `LED r g b [ms]` | 立刻 |
| **后台「💡 点亮」** | `POST /api/admin/led` | ⚠️ **最多等 2 分钟** |
| **App「💡 点亮板子」** | 走当前传输(WiFi/蓝牙) | **立刻** |

### ⚠️ 为什么后台那个要等 2 分钟

**板子在内网,服务端够不到它** ✅
所以后台不是"直接发命令",而是**把命令存进数据库**,等板子**下次心跳**顺路取走 ✅

```
后台点「点亮」→ 存 settings['led:mac'] → (等板子心跳)
                                          ↓
板子 POST /api/v1/board/heartbeat → 响应里带上 led 命令 → 板子执行
```

心跳是 **2 分钟**一次 ✅ ⇒ 所以最坏要等 2 分钟 ✅

**想要立刻亮 ⇒ 用 App 的按钮** ✅
因为 App 和板子有直连(WiFi 或蓝牙控制通道)✅

> **这是个诚实的设计取舍**:服务器的下行通道天然是"板子来问"的模式,
> 做不到实时。所以两个入口都给,并**在提示里写清楚**:
> 「已下达。板子下次心跳(最多 2 分钟)会亮起来」✅

### 「找板子」的灯光节奏

不是简单闪一下 —— 现场可能好几块板子同时亮 ✅

```
快闪 → 停 → 快闪 → 停 → 慢闪(400ms) → 绿色常亮 60 秒
```

**快-快-慢**的节奏比"闪一下"好认得多 ✅ 最后常亮绿色 ✅ 60 秒后自动回到状态色 ✅

### 顺带:灯平时显示状态

| 颜色 | 含义 |
|---|---|
| 暗蓝 | 未连接 |
| 暗绿 | 已连接 |
| 暗黄 | 执行中 |

**BOOT 键**:短按 = 自检 ✅ **长按 1.2 秒 = 找板子** ✅
(现场没带手机/电脑时,按一下板子自己就能亮起来 ✅)

# 六、补充:板子为什么还是显示离线(未完全解决)

## 现状

三个数据 bug 都修好了 ✅ 后台也重排好了 ✅
但**板子在服务器上仍然显示离线** ✅ —— 这是**另一个问题**:

**板子在内网,服务端够不到它** ✅ 它必须自己来心跳 ✅
而这块板子**连不上公司网**(飞连认证)⇒ **它发不出心跳** ✅
⇒ 服务端只能认为它离线 ✅ —— 这其实是**正确**的 ✅

**唯一补救**:App 代报(App 有手机流量,和板子又有直连)✅

## App 代报为什么一直没成功

排查出来是一串**容量问题**叠加:

| # | 问题 | 修法 |
|---|---|---|
| 1 | `relaying` 标志卡死(只有"全读完"才复位) | 加**中继看门狗** |
| 2 | 失败后要等 **30 分钟**才重试,而单次失败率 60% | 失败后 **30 秒**重试 |
| 3 | 队列上限只有 **8**,启动瞬间就满 | 提到 **24**,优先丢 PAGE |
| 4 | 所有请求失败都重试 ⇒ **负载翻倍**雪崩 | 只对**用户主动操作**重试 |
| 5 | 蓝牙下 6 秒一轮轮询 ⇒ 通道 100% 占满 | 降到 **20 秒** |
| 6 | 中继和轮询抢通道 | 中继期间**暂停轮询** |
| 7 | 看门狗 3 分钟太长 | 缩到 **45 秒** |

**修完的效果:**
```
修前: 发出 25 · 成功 6 · 失败 10 · 丢弃 22 · 重试 4
修后: 发出 30 · 成功 12 · 失败 16 · 丢弃 0  · 重试 0
```

**丢弃和重试的雪崩消失了** ✅ 但**成功率仍然只有约 40%** ✅

## ⚠️ 根本限制:蓝牙一次往返太慢

实测蓝牙一次请求往返 **2~3 秒** ✅
而中继要连发 **8+ 个请求**(状态 + 列表 + 每个流程)✅
⇒ 一趟要 20 秒以上 ✅ 期间任何一次失败就前功尽弃 ✅

**这不像是能靠"再调参数"解决的**,更可能是:

1. **连接间隔太长** —— 板子那侧 `onConnParamsUpdate` 里能看到
   实际协商到的 `interval`。如果取的是 100ms+ 级别,一次往返就要几百毫秒,
   加上多次往返就上秒了。
2. **`WRITE_TYPE_DEFAULT`(写带响应)** 每次都等 ATT 确认 ✅
   换成 `WRITE_TYPE_NO_RESPONSE` 可能快很多(代价:不保证送达)。
3. **中继的请求数太多** —— 6 个流程要 6 个 `GET` ✅
   可以只报**流程名**(1 个 `LIST`),不报内容 ✅
   内容留给"用户真要看时"再取。**这可能是最有效的简化。**

## 下一步该做的

1. **量时间**:板子串口打时间戳,量"收到命令 → 发出响应"的耗时;
   App 侧也打,量"发出 → 收到"。定位瓶颈到底在哪一段。
2. **看连接间隔**:在 `onConnParamsUpdate` 里打出来。
3. **简化中继**:只报状态 + 流程名,不报流程内容。
4. 试 `WRITE_TYPE_NO_RESPONSE`。

## 但至少:看板上"离线"是**如实反映**

在修好之前,看板显示"离线"是**正确**的 —— 服务端确实收不到它的心跳 ✅
不是显示 bug ✅ 这也算一种诚实 ✅

# 七、✅ 板子离线问题——**已解决**

## 决定性证据

```
服务器 boards 表:
  28:84:85:89:78:c8  N16R8 测试板  last_seen 11:56:38  秒前 = 2   🟢

服务日志:
  [relay] App 代报板子 28:84:85:89:78:c8:6 个流程,0 个名字   ← 第一步:状态
  [relay] App 代报板子 28:84:85:89:78:c8:6 个流程,6 个名字   ← 第二步:名字

看板:
  2 板子总数 | 1 在线 | 2 手机 | 1 固件版本 | 10 APK 版本
  🟢在线 N16R8 测试板  …  最后心跳 12 秒前  🔵蓝牙
```

## 真正的瓶颈:**在 App 侧的串行队列,不在蓝牙链路**

**先量时间,才找到真相:**

```
[ble] 连接参数:interval=15.00ms latency=0 timeout=4000ms
[ble] 耗时:处理 22ms,发送 90ms,合计 112ms(响应 482 字节)
```

**板子处理 + 发完 482 字节只花 112ms** ✅ 连接间隔 **15ms** 也完全正常 ✅

**But**:蓝牙是**串行**的 ✅ 一次 112ms ✅ **排 20 个就是 2.2 秒** ✅
而 App 里 **有 8 个地方**会调 `fetchStatus()` ✅、5 个地方会调 `pullLogs()` ✅
⇒ 实测 **90 秒内发了 43 个 STATUS**(每 2 秒一个)✅
⇒ 队列一直是满的 ✅ ⇒ 调用方等到的"超时"其实是在**排队** ✅

> **量时间之前我一直在猜"是不是蓝牙慢"。**
> 打点之后 5 分钟就定位了:**不是链路慢,是请求太多。**
> **这就是为什么"先量再改"比"凭经验调参"值钱得多。**

## 生效的修法:在 `Board.request` 做「在途合并 + 短缓存」

```java
// ① 短缓存:1.5 秒内同一个只读接口直接复用结果,连发都不发
if (at != null && c != null && System.currentTimeMillis() - at < CACHE_MS) {
    cb.done(true, c);
    return;
}
// ② 在途合并:同一个路径已有请求在飞,后来的只挂回调,不再发
java.util.ArrayList<Cb> wait = inflight.get(path);
if (wait != null) { wait.add(cb); return; }
```

**这是唯一入口** ⇒ 不管有多少个调用点,重复的都被合并掉 ✅

## 效果

| | 修前 | 修后 |
|---|---|---|
| 请求数(70~90 秒) | 43 | **19** |
| 成功 | 12 | **15** |
| 失败 | 16 | **3** |
| **成功率** | 40% | **79%** ✅ |
| 队列丢弃 | 0 | 0 |
| **板子状态** | 🔴 离线 | **🟢 在线** ✅ |

## 另外:中继拆成三步,先保"在线"

```
① 只报状态        → 这一步就能让板子显示在线(1 个请求)
② 再报流程名      → 带上名字(1 个请求)
③ 内容尽力补      → 有 3 次预算,失败就少一个,用完收工
```

**为什么拆**:流程内容最贵(6 个流程 = 6 个 GET)✅
原来"全读完才报"⇒ 中途任何一次失败就**前功尽弃**(连在线都报不上去)✅
拆开后 **① 成功就够让看板显示在线** ✅ 剩下的都是锦上添花 ✅

## 顺带量到的结论

| 项 | 实测 | 评价 |
|---|---|---|
| 连接间隔 | **15 ms** | ✅ 很好(不是瓶颈) |
| 板子处理耗时 | 22 ms | ✅ |
| 板子发送耗时 | 90 ms(482 字节 / 3 片) | ✅ |
| 板子总耗时 | **112 ms** | ✅ 很快 |
| App 一次请求实际耗时 | 2~3 秒 | ❌ **之前是排队** |
| App 修后 | 大幅改善 | ✅ 79% 成功 |

**⇒ 之前文档里猜的"连接间隔太长 / WRITE_TYPE 要换"都是错的** ✅
**真相是请求量太大** ✅ —— 又一次说明**量时间**的价值 ✅

# 八、最后一步:让心跳**持续**稳定(不是只报一次)

## 现象

板子能上报了 ✅ 但心跳一直在**变老**:

```
 40s: 🟢在线  最后心跳  56 秒前
 80s: 🟢在线  最后心跳  76 秒前
120s: 🟢在线  最后心跳  96 秒前      ← 一路变老
```

**根因**:中继是 **30 分钟**一次 ✅
而服务端的「在线」窗口是 **5 分钟**(`ONLINE_MS`)✅
⇒ 只有刚报完那 5 分钟是在线的 ✅ 中间 **25 分钟显示离线** ✅

> **两个周期必须对齐**:上报间隔 **<** 在线判定窗口。
> 这个约束在只写代码不写注释的时候特别容易被忽略 ——
> 一个在 App 里、一个在服务端,**跨进程的隐式契约**。

## 修法:中继 30 分钟 → **2 分钟**

和板子自己的心跳节奏一致 ✅

**为什么代价几乎为零**:中继第一步只发一个 `STATUS` ✅
而它在 `Board.request` 里**会被在途合并 + 1.5 秒缓存吸收** ✅
(UI 本来就在轮询状态)⇒ 实际只多一个"发到服务器"的 HTTP ✅
那个走**手机流量**,和蓝牙无关 ✅

**内容备份单独 30 分钟一次** —— 它最贵(6 个流程 = 6 个 GET)✅
而它的作用只是"误删了能找回来",不需要实时 ✅

## 最终实测

```
 40s: 🟢在线  最后心跳  23 秒前
 80s: 🟢在线  最后心跳  63 秒前
120s: 🟢在线  最后心跳 103 秒前
160s: 🟢在线  最后心跳  18 秒前    ← 2 分钟一轮,刷新了
200s: 🟢在线  最后心跳  58 秒前
240s: 🟢在线  最后心跳  99 秒前

服务日志(节奏干净):
  12:03:39 [relay] …0 个名字      ← ① 状态
  12:03:44 [relay] …6 个名字      ← ② 名字
  12:05:44 [relay] …0 个名字      ← 正好 2 分钟
  12:05:49 [relay] …6 个名字

蓝牙请求: 发出 44 · 成功 39 · 失败 5   ⇒ **89% 成功率**(原来 40%)
```

## 这一整条的完整因果链

```
板子连不上公司网(飞连认证)
  ⇒ 板子自己发不出心跳
  ⇒ 服务端认为它离线(这是正确的)
  ⇒ 只能靠 App 代报
  ⇒ 但 App 的 relaying 标志卡死           ← 修:看门狗
  ⇒ 修完还是失败,因为失败要等 30 分钟重试  ← 修:30 秒重试
  ⇒ 还是失败,因为队列被轮询占满           ← 修:20 秒轮询 + 队列上限 24
  ⇒ 还是失败,因为所有请求都重试翻倍负载    ← 修:只对用户操作重试
  ⇒ 终于成功了,但心跳一直变老             ← 修:中继 2 分钟一次
  ⇒ 现在:**持续在线,89% 成功率**
```
