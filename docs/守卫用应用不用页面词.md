# 现象与证据

用探测流程在大麦的 H5 页面上跑一遍,日志直接把原因写出来了:

```
[2/15] 等待页面:1张                     → 超时(那页上没有「1张」)
         当时页面:cn.damai.h5container.DMH5Activity
         那页上的词:大麦AI / 点击查看近3天历史 / 内容由 AI 大模型生成… /

[3/15] 如果是页面:1张                   → ❌不匹配,跳到第 6 步
[6/15] ❌ 页面词守卫 拦住 这就是流程不动的原因
```

**那一页上根本没有「1张」**(也没有「预约」「可预约」)——
所以我的每一个 `ifpage` 都不匹配 ⇒ **一个点击都不做** ⇒ "不动了" ✅

# 两种守卫的区别(关键)

| 守卫写法 | 匹配条件 | 抢票链路(跨多个 H5 页) |
|---|---|---|
| `ifpage 抢票预约`<br>`ifpage 1张`<br>(**页面词**) | 页面的**文字**里有这个词 | ❌ **H5 页词不固定 → 误判成"不在目标页" → 整条链路跳过** |
| `ifpage @cn.damai`<br>(**应用级**) | **Activity** 里含 `cn.damai` | ✅ **大麦的任何页面都匹配** |

**`@` 前缀是"只匹配 Activity 名"** —— 这就是它能跨页面生效的原因。

## 实测对比(同一页,同一次运行)

```
[2/15] 等待页面:1张           → 超时      （页面上没这个词）
[3/15] 如果是页面:1张         → ❌ 不匹配  ← 旧设计在这里失败
[6/15] ❌ 页面词守卫 拦住

[9/15] 等待页面:@cn.damai     → ✅ 页面已出现(等了 1 ms)
[10/15] 如果是页面:@cn.damai  → ✅ 匹配    ← 新设计正确
[11/15] ✅ 应用级守卫 放行
```

```

T 0.631 0.419 30 点击抢票预约      ← waitfor 失败也**照样点**
```

**`waitfor` 超时不会中断,`T` 一定会执行。**

# 新流程:应用级守卫

新建了 **`大麦抢票-应用级守卫版`**(41 步),替换掉那个坏的 ifpage 版:

```
 1. wait 1 ① 确认大麦在前台
 2. waitfor @cn.damai 10000              等大麦出现(开屏广告会自动等)
 3. ifpage @cn.damai
 4.   waitfor 首页 5000                   等首页加载完
 5.   T 0.9 0.914 30                      点底部「我的」
 6. else
 7.   wait 1 大麦不在前台 整个流程跳过 不乱点
 8. endif

 9. wait 1 ② 我的页 进抢票预约
10. waitfor 我的 3000                     只负责"等"
11. waitfor @cn.damai 2000                确认还在大麦
12. ifpage @cn.damai
13.   T 0.631 0.419 30                    点「抢票预约」
14. else
15.   wait 1 不在大麦 跳过
16. endif
... (后面三处同理)
41. wait 1 流程结束
```

## 设计原则(和原来完全不同)

| | 旧版(坏的) | 新版 |
|---|---|---|
| `waitfor` 的作用 | 兼作"能不能点"的判断 | **只负责"等",不参与判断** |
| 点击条件 | 页面上有具体词 | **只要还在大麦里就点** |
| 页面变了 | ❌ 直接跳过不点 | ✅ 照点(H5 页面布局是固定的) |
| 跳出大麦了 | ❌ 可能乱点 | ✅ 跳过不点 |

**一句话:`waitfor` 用来等,`@应用名` 用来保命。**

# 什么时候该用哪种守卫

| 场景 | 推荐 |
|---|---|
| **链路跨多个 H5 / 动态页面**(抢票、秒杀) | **`@应用名`** —— 页面词靠不住 |
| **单页操作,页面结构稳定** | 页面词(可以用 🔍 挑 ⭐ 的) |
| **只想确认"没跳出目标 App"** | `@应用名` |
| **要区分"同一个 App 里的不同页"** | 页面词 —— 但**必须用该页独有的词** |

> ⚠️ **最坑的中间情况**:用**底栏页签**这种"每页都有"的词当守卫 ——
> 看起来在判断,其实**永远匹配**,等于没判断。
> 详见 [`智能等待怎么用.md`](智能等待怎么用.md) 的 ⭐ 机制。

# 顺带修掉:又一个 UTF-8 截断

读 `/api/page` 时报:

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe7 in position 328
```

```cpp
void setPageInfo(const char *act, const char *text) {
  strncpy(s_pageText, text, sizeof(s_pageText) - 1);   // ← 从中文中间切
}
```

`s_pageText` 是 256 字节,页面文字是中文(3 字节/字)——
`strncpy` 在第 255 字节处**从字符中间切断** ⇒ 非法 UTF-8 ⇒ 整个响应解析失败 ✅

**修法**:改用 `utf8Truncate`(之前提成公共函数那个):

```cpp
if (text) utf8Truncate(s_pageText, text, sizeof(s_pageText));
if (act)  utf8Truncate(s_pageAct,  act,  sizeof(s_pageAct));
```

**修后**:`/api/page` 正常返回 ✅

> 这是**第四次**踩 UTF-8 截断了(备注、`/api/status`、`copyNote`、`setPageInfo`)。
> **凡是写字符串的地方都该用 `utf8Truncate`** —— 靠记性是不行的。

# 教训

## 1. "更安全"的改动可能把能用变不能用

我加守卫的初衷是防止"超时后乱点",但**守卫本身判断错了**,
结果从"偶尔点错"变成"**完全不动**" —— 对抢票来说后者更糟。

**改一个能工作的流程前,先想清楚:新逻辑失败时会怎样?**
我这次的失败模式(什么都不做)比原来的失败模式(偶尔点错)更致命。

## 2. `waitfor` 和 `ifpage` 的职责要分清

- `waitfor` = **等**(失败了继续走,是"希望")
- `ifpage` = **判断能不能做**(失败了跳过,是"守卫")

**两个都用来当守卫,就会像我这次一样:等待条件不满足 ⇒ 动作被跳过。**

## 3. 判断条件要选"稳定"的信号

Activity 名(`@cn.damai`)在整个 App 生命周期内稳定;
页面文字在 H5 页面上千变万化。

**选那个不会因为页面刷新而变的信号。**
