>

> **用户已澄清:那些流程是他自己删除的。**


**流程的 x≈963 与「删除」的 x=926 落在同一列** —— 点击热区有余量时会命中。

## 二、真实存在的漏洞:**定时执行不锁界面**

```java
// 手动点「运行」:有锁 ✅
exec(...) → setRunning(true)   → 盖"执行中遮罩",按钮不可点

// 定时自动执行:没锁 ❌
board.run(idx, times, gap, silent);   // 直接调板子,界面完全不设防
```

所以:**如果定时到点时本 App 正好在前台**,流程的注入点击是有可能点到我们自己的按钮的。

这个漏洞与"那次删除"无关,但**客观存在**,已修。

## 三、加固措施(预防)

### 1. 定时执行也走 `exec()`(上锁)

```java
// 改前
board.run(idx, times, gap, silent);

// 改后
exec(idx, times, gap);     // 内部会 setRunning(true) 盖遮罩
```

### 2. 「停止执行」改成**长按**

遮罩中间的停止按钮,如果流程正好点屏幕中央(`T 0.5 0.5` —— 用户流程里就有),
普通点击会被误触发把流程停掉。

```java
stop.setOnLongClickListener(...);   // 长按 1.5 秒才停
stop.setText("长按停止");
```

一般 tap 是 30~60ms,远短于长按。

## 四、教训

> **注入型应用必须假设"注入的点击可能落在自己身上"。**
>
> 只要界面上有可点元素、而坐标来自外部(用户录的 / 拾取的),
> 就一定存在"撞上"的可能。
>
> 所以:**执行期间无条件锁住自己的界面**,而且锁里不能有"一点就生效"的破坏性按钮;
> **两条执行路径(手动 / 定时)必须共用同一套保护。**
