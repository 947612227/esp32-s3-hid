# 板子的灯:控制链路 + 怎么关 / 怎么改颜色

# 〇、控制链路(**不是** 服务器→App→板子)

**一共五条路**,按"生效快慢"排:

```
① 串口            电脑 ──USB串口线──> 板子 COM 口           立刻
② 板子 HTTP       同一WiFi的设备 ──> http://<板子IP>/api/led  立刻
③ 蓝牙控制通道     App ──BLE GATT(A5C1/A5C2)──> 板子        立刻
④ App「💡灯」按钮  ──> 走 ② 或 ③(蓝牙就绪就走蓝牙)          立刻
⑤ 后台「💡灯」按钮 后台 ──> 服务器 ──存库──> ...              最多 2 分钟
```

## ⚠️ 第 ⑤ 条**不经过 App 的"转发"**,而是**板子自己去拉**

```
后台(浏览器)
   │  POST /api/admin/led  {mac, mode}
   ▼
服务器  ──写入──>  MySQL settings 表  k='led:<mac>'
                        ▲
                        │  ① 板子自己有网时:板子心跳时取走
                        │     POST /api/v1/board/heartbeat → 响应里带 led
                        │
                        │  ② 板子没网时(**你现在就是这样**):
                        │     App 代报时取走
                        └──   POST /api/v1/app/board-relay → 响应里带 led
                             → App 再通过 ③ 蓝牙通道 / ② 局域网 HTTP
                               下发给板子(立刻)
```

**核心是"板子来问,顺路捎回去"** ✅ —— 因为板子在内网,服务器**够不到它** ✅

## 🐛 这里原本有个断层(已修)

设计时只做了"板子自己心跳来取" ✅
但**这块板子连不上外网**(公司网要飞连认证,只能开热点)⇒ **它永远发不出心跳** ✅
⇒ 后台存的命令**没人来取** ⇒ **后台「💡 灯」看着成功,板子毫无反应** ✅

**修法**:让 **App 代报时顺路把命令取走**,再通过直连下发给板子 ✅
(见 `server/index.js` 的 `/api/v1/app/board-relay` 和 App 的 `applyServerLed()`)

**实测:**
```
① 后台下达「红」  → {"ok":true,...}
② 命令进库       → led:28:84:... = {"r":255,"g":0,"b":0,"ms":0}   ✅
③ 中继一次       → {"ok":true,"led":{"r":255,"g":0,"b":0,"ms":0}}  ✅
④ 库里剩余命令   → 0                                              ✅ 取走即删
```

## 怎么选

| 场景 | 用哪条 |
|---|---|
| 就想马上看到效果 | **App 的「💡 灯」**(④,直连) |
| 手边有电脑接了串口 | **串口**(①,最快) |
| 只想在后台点一下 | **后台**(⑤,等 ≤2 分钟;前提是 App 在跑或板子自己有网) |

> ⚠️ **后台那条依赖 App 在运行**(或板子自己有外网)✅
> 如果 App 被杀掉了、板子也没网,后台点的灯**不会生效** ✅

# 〇之二、⚠️ 状态灯"不跟着流程变色"的两个坑(已修)

用户实测反馈:**"跑了个流程,灯还是红的,没变色,也没灭"** ✅
颜色本身是对的(说明 GPIO48 没搞错 ✅),问题在**状态切换没生效** ✅

## 坑 ① 在 main loop 里"轮询"运行状态 —— 永远看不到

```cpp
// 错的(我第一版)
bool running = netManager().isRunning();
if (running) Led::setState(Led::ST_RUNNING);
```

**为什么必然失效**:流程是在 `netServiceScripts()` 里**同步跑完**的 ✅
`s_state.running` 在**同一次函数调用里**先置 `true`、跑完再置 `false` ✅
而主循环一轮才看一次 ⇒ **永远看不到中间的 `true`** ✅

## 坑 ② 修错了地方 —— 串口 RUN 绕过了那条路

第二版我把灯放进 `netServiceScripts()` ✅ 结果**串口跑流程还是不变色** ✅

因为那个函数有两个限制:
```cpp
if (sc && Touch.ready() && !s_state.running) {   // ① 要求手机 HID 已连
```
② 而且只有 **Web / BLE** 触发的执行才走它 ✅
**串口 `RUN` 是在 `main.cpp` 里直接调 `Scripts.run()` 的** ✅ 完全绕过 ✅

**串口日志是决定性证据**:
```
[script] 执行 [1] 向下滚动 (6 步)
（没有 "[led] 状态色 → 黄(运行中)"）      ← 我加的代码压根没执行
```

## ✅ 最终修法:放进 `Scripts::run()` 里(唯一的必经之路)

```cpp
// script_engine.cpp 的 run()
Led::setState(Led::ST_RUNNING);   // 开头 → 黄
  ... 跑步骤 ...
Led::finished();                  // 结尾 → 绿 5 秒
```

**为什么这样对**:不管从**串口 / HTTP / BLE / 定时调度**哪个入口进来 ✅
最终都汇到 `Scripts::run()` 这一个函数 ✅ —— **唯一必经之路** ✅

## 坑 ③ 绿光被立刻盖掉

```cpp
// setState 原来只判"手动常亮"
if (s_manual && s_holdUntil == 0) return;
```

`finished()` 设好 5 秒绿 ✅ 主循环下一轮就 `setState(ST_IDLE)` ✅
**不检查那个 hold** ⇒ 绿被**立刻**盖成红 ✅

**修**:加一条
```cpp
if (s_holdUntil && millis() < s_holdUntil) return;   // 限时色保持期内不许盖
```

## 实测(带时间戳的串口日志)

```
[  1.22s] [led] 状态色 → 黄(运行中)      ← 流程开始
[  3.65s] [led] 执行结束 → 绿 5 秒
[  8.74s] [led] 状态色 → 灭(闲置)        ← 8.74 − 3.65 = **5.09 秒** ✅
```

> **一句话教训:状态变化要用"事件驱动",不要用"轮询"。**
> 尤其当状态在一个函数里瞬时翻转时,轮询必然漏掉 ✅

# 〇之三、🌈 四色自检(LEDTEST)—— 现场确认灯好不好用

## 为什么需要

黄只亮**流程那么久**(实测 2.5 秒)✅ 绿只亮 5 秒 ✅
**跑完你回头看板子时已经回红了** ⇒ 很容易以为"灯根本没变" ✅

所以加了这条:把四个颜色**依次**亮一遍,一眼就能确认 ✅

## 怎么用

| 入口 | 命令 |
|---|---|
| **App** | 状态页 →「💡 点亮板子」→「🌈 四色自检(红→黄→绿→灭)」 |
| **串口** | `LEDTEST`(或 `LED TEST`) |
| **蓝牙控制通道** | `LED TEST` |
| **HTTP** | `GET /api/led?mode=test` |

**行为**:红 → 黄 → 绿 → 灭,各 **1.5 秒**,走完自动回到"自动"模式 ✅

## 怎么判读

| 现象 | 说明 |
|---|---|
| 四个颜色**都能看到** | ✅ 灯和引脚都对,状态机也没问题 |
| **只亮一个色**,其它不变 | ⚠️ 灯珠只有那一个通道好(或引脚只有那种极性) |
| **完全不亮** | ⚠️ 引脚不对 ⇒ 试 `LEDPIN 38` / `LEDPIN 21` |
| 亮的是**别的颜色** | ⚠️ RGB 顺序不对(有些模块是 GRB 不是 RGB) |

# 〇之四、💡 「灯到底什么色」现在 App 上能直接看

## 为什么加

用户实测反馈:"跑流程只看到红灯" ✅
但查下来**固件是对的**(串口日志证明 黄→绿→红 都发生了)✅
**问题是**:黄只亮流程那么久(实测 2.5 秒)、绿 5 秒 ✅
用户一按运行就去看**手机有没有动** ✅ 回头看板子**已经回红了** ✅

**⇒ 让人"盯板子"是不靠谱的设计** ✅ 所以把状态**报出来** ✅

## 怎么做的

`/api/status` 里多一个字段:
```json
{ "run": { "running": true, ... }, "led": "黄(运行中)", ... }
```

App 状态页的「连接方式」卡里多一行:
```
💡 灯:自动(随状态)
```

**跑流程时它会变**:`自动(随状态)` → 运行中是「黄(运行中)」✅

## ⚠️ 踩的坑:字段加对了,但**固件没重编**

`/api/status` 加了字段 ✅ 代码位置也对 ✅ 但 App 上一直显示 `💡 灯:—` ✅
**原因**:PlatformIO 的增量编译**没重编 `net_manager.cpp`** ✅

**修**:删掉目标文件强制重编
```bash
find .pio/build/ble -name "net_manager*.o" -delete
pio run -e ble
# 然后验证固件里真的有这个字段
strings .pio/build/ble/firmware.bin | grep -c '"led"'
```

> **教训:改了 C++ 却发现"没生效"时,先确认目标文件真的重编了。**
> 光看 `pio run` 报 SUCCESS 是不够的 ✅

# 〇之五、⚠️ "点了运行要等 30 秒才执行"(实测反馈,已修)

## 现象

> 用户:"很多时候执行了流程**会等超时,然后再执行**,例如「最近任务」,
>       **超时后才开始执行的**,大概等了 **30 秒**"

## 根因:App 的**重试**机制 + 通道拥堵

```java
// Ble.java
requestRaw(cmd, timeoutMs, new Cb() {
    public void done(String body) {
        if (body != null || left <= 0) { cb.done(body); return; }
        Log.i("TouchBle", "重试(" + left + "):" + cmd);
        requestOnce(cmd, timeoutMs, left - 1, cb);   // ← 超时就重试
    }
});
```

**完整因果链**:
```
用户点「运行」
  → RUN 入到 App 的 BLE 队列
  → 但队列**前面堵着**:20 秒周期轮询(STATUS/LOG)+ 中继读流程(大响应)
  → RUN 迟迟发不出去,或者发出去了响应回不来
  → 超时
  → App **重试**(isUserAction 认为 RUN 该重试)
  → 这次终于发出去了
  → 流程**这才开始跑**        ← 用户看到的"等 30 秒才动"
  → 而且因为**重试过**,板子可能**跑了两遍**
```

## 修法

### ① 用户动作期间,**周期轮询全部让路**

```java
// MainActivity.netTick
if (Ble.userActionPending()) {
    ui.postDelayed(this, 1500);
    return;                 // 12 秒内不发任何周期请求
}
```

`Ble.noteUserAction()` 在 RUN/STOP/SAVE/DEL 发起时打时间戳 ✅
**让路 12 秒** ⇒ 用户操作独占通道 ⇒ 立刻生效 ✅

### ② "运行中黄"至少亮 5 秒

```cpp
// script_engine.cpp 的 run()
const uint32_t ledRunT0 = millis();     // 开头记时
  ... 跑步骤 ...
{ // 结束前补足
  uint32_t elapsed = millis() - ledRunT0;
  if (elapsed < 5000) delay(5000 - elapsed);
}
Led::finished();
```

**为什么**:1 步的「最近任务」只跑不到 1 秒 ✅ 黄一闪而过 ✅
用户会以为"灯没变" ✅ 补足到 5 秒就看得清了 ✅

> **教训:"用户主动操作"和"后台轮询"共用一条慢通道时,必须给用户操作让路。**
> 否则用户看到的是"点了没反应",而系统以为是"超时重试成功了" ✅

# 一、你看到的蓝灯是什么

## 先说清楚:你看到的蓝灯是什么

板子刚上电时灯是**暗蓝色** —— 这是**「自动」模式下的状态色**:

| 颜色 | 含义 |
|---|---|
| **暗蓝** | 未连接(手机没连上板子) |
| 暗绿 | 已连接 |
| 暗黄 | 流程执行中 |

**所以灯是蓝的 = 板子现在没被手机连上** ✅ 这不是故障 ✅

---

## 怎么关

### 方法一:App(推荐,立刻生效)

App → **状态页** → 「💡 点亮板子」按钮(现在改叫「💡 灯」)→ 选 **⚫ 关灯** ✅

### 方法二:后台

`http://120.55.183.206/admin/` → **控制中心** → 板子那行点 **💡 灯** → 选 **⚫ 关灯** ✅

⚠️ **后台要等最多 2 分钟**才生效 ✅
因为服务端**够不到内网的板子**,只能把命令存起来,等板子下次心跳(2 分钟一次)取走 ✅
**App 那条路是直连,立刻生效** ✅

### 方法三:串口(最快)

用串口工具(115200)连板子的 COM 口,发:

```
LED OFF
```

## 怎么改成指定颜色

三种方式都有,命令一样:

| 想亮的颜色 | 命令 / 选项 |
|---|---|
| 🔴 红 | `LED 255 0 0` |
| 🟢 绿 | `LED 0 255 0` |
| 🔵 蓝 | `LED 0 0 255` |
| 🟡 黄 | `LED 255 180 0` |
| 🟣 紫 | `LED 180 0 255` |
| ⚪ 白 | `LED 255 255 255` |
| ⚫ 关灯 | `LED OFF`(等同于 `LED 0 0 0`) |
| 🔄 回状态色 | `LED AUTO` |

**App / 后台**里就是那个「💡 灯」对话框里的按钮 ✅

**亮度自己调**:每个通道 0~255 ✅ 比如 `LED 20 0 0` 就是很暗的红 ✅

## ⚠️ 一个重要的行为变化(这次新加的)

**手动设的颜色 / 关灯会「锁住」** ✅

以前的问题:

```
你手动把灯设成红色 / 或者关掉了
  → 手机一连上板子
  → 状态色把它盖成绿色 / 又亮起来
  → 你看着莫名其妙:"我明明关了它怎么又亮了"
```

现在:

```
手动设过颜色之后 = 进入「手动模式」
  → 状态变化**不会**再动它
  → 要显式选「🔄 回到自动」才交还给状态色
```

**怎么知道自己现在在哪个模式** —— 串口发 `LED`(不带参数)会告诉你:

```
LED 当前模式:自动(随状态)
```
或
```
LED 当前模式:手动色
```
或
```
LED 当前模式:关灯(手动)
```

## ⚠️ 这次修掉的一个隐蔽 bug

`LED AUTO` / `LED OFF` 一开始**报"用法错误"** ✅ 而 `LED 255 0 0` 却正常 ✅

根因:

```cpp
// 上游拆词:
char word[16]; sscanf(line, "%15s", word);
const char *rest = line + strlen(word);   // "LED AUTO" → rest = " AUTO"(带前导空格!)

// 我的判断:
if (!strcasecmp(args, "AUTO")) { ... }    // " AUTO" ≠ "AUTO" ❌
```

**为什么 `LED 255 0 0` 能过**:`sscanf` 会自动跳过前导空白 ✅
所以这个 bug **只在纯字母参数上暴露** ✅ 特别隐蔽 ✅

而其它 handler(`RUN`/`DEL`/…)开头都有 `while (*args == ' ') args++;` ✅ —— 我漏了 ✅

> **教训:同一个文件里别人怎么写,往往就是"这里有个坑"的提示。**
> 那几个 `while (*args == ' ')` 不是废话,是在绕一个真实的坑 ✅
