# 一、新指令:`notify`

```
notify <消息内容>
```

执行到这一步,**板子会 POST 给控制中心**,服务器存进 `board_events` 表,
看板上的「🔔 流程事件」能看到。

## 你的抢票流程(已更新到板上)

```
 4. repeat 30
 5. T 0.801 0.911 30 ① 点「立即提交」
 6. waitfor 继续尝试 2500 ② 最多等 2.5 秒
 7. ifpage 继续尝试
 8. T 0.522 0.594 30 ③ 点「继续尝试」
 9. else
10. wait 1 ③ 没弹,可能已经跳去付款了
11. endif
12. ifpage 支付宝付款 ④ 每轮都查一次
13. notify 抢到了!页面已跳到付款 快去付款      ← 就是这一行
14. break 抢到了 跳出循环去付款
15. endif
16. wait 300 进入下一轮
17. endloop
```

**`notify` 写在 `ifpage` 里面,所以只有真的跳到付款页才会发。**

## `notify` 的细节

| 项 | 说明 |
|---|---|
| 消息内容 | **整行都算**(后面的中文不会丢) |
| 长度 | 最多 72 字节(中文约 24 字) |
| 失败时 | **不重试、不中断流程** —— 只记一行日志。抢票不能因为网络问题卡住 |
| 前缀 | 板子日志里带 `[app]`/`[net]`,服务器表里带流程名 |

# 四、这次顺带挖出来的**两个严重问题**

## 问题 ① 一个 SQL 报错把**整个服务器搞下线了**

加完接口后调了一次,结果:

```
Error: Illegal mix of collations (utf8mb4_unicode_ci) and (utf8mb4_0900_ai_ci)
       for operation '='
touchpad-server.service: main process exited, code=exited, status=1/FAILURE
touchpad-server.service failed.          ← 整站下线,而且不自己起来
```

### 根因有两层

**第一层:建表时没指定排序规则**

MySQL 8 的库默认是 `utf8mb4_0900_ai_ci`,而这个库早期建的 14 张表都是
`utf8mb4_unicode_ci`。我 CREATE TABLE 时没写 COLLATE,于是新表用了库默认值 ⇒
和 `boards.mac` JOIN 时报 **Illegal mix of collations** ✅

**第二层(更严重):未捕获的 Promise 异常直接杀进程**

`await db.q(...)` 抛错,Express 4 的 async 处理不会自动 catch ⇒
变成 unhandledRejection ⇒ **Node 默认直接退出** ✅
而 systemd 单元里**没有 `Restart=`** ⇒ 服务一直 `failed` ✅

### 修法(三处)

```diff
- CREATE TABLE board_events (...) ;
+ ALTER TABLE board_events CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

+ // 全局兜底:一个坏请求不该让整站下线
+ process.on('unhandledRejection', (err) => console.error('[未捕获的 Promise 异常]', err));
+ process.on('uncaughtException',  (err) => console.error('[未捕获的异常]', err));

+ // events 接口套 try/catch + JOIN 显式 COLLATE
```

```ini
# /etc/systemd/system/touchpad-server.service.d/restart.conf
[Service]
Restart=always
RestartSec=3
StartLimitIntervalSec=0
```

### 验证

```
畸形请求 HTTP 401
之后服务 HTTP 200   ← 没被搞死
服务状态: active
Restart=always  RestartUSec=3s
```

> **教训:任何 HTTP 接口都必须自己 catch 异常。**
> Express 4 不会替你兜 async 里的 rejection ——
> **一次数据库报错就能让整个服务下线**,而且不重启就一直躺着。

## 问题 ② 板子日志又是 UTF-8 截断(第 5 次!)

`/api/logs` 返回的 JSON 解析失败:

```
UnicodeDecodeError: invalid continuation byte
```

元凶:

```cpp
char tmp[LOG_LINE_LEN];                  // 160 字节
vsnprintf(tmp, sizeof(tmp), fmt, ap);    // ← 按**字节**截断
```

中文 3 字节/字,第 160 字节很可能落在字符中间 ⇒ 非法 UTF-8 ⇒
**整个日志响应解析不了** ✅

### 我的第一版修复**差了一位**

```cpp
size_t n = strlen(tmp);
while (n > 0 && ((unsigned char)tmp[n] & 0xC0) == 0x80) n--;   // ❌
```

`tmp[n]` 是 **NUL 终止符**,不是最后一个字符 ✅ 判断永远不成立 ✅

**正确写法 —— 从最后一个字节往回找:**

```cpp
size_t len = strlen(tmp);
size_t i = len - 1;
while (i > 0 && ((unsigned char)tmp[i] & 0xC0) == 0x80) i--;  // 退到该字符首字节
unsigned char c = (unsigned char)tmp[i];
size_t need = (c < 0x80) ? 1 : ((c & 0xE0) == 0xC0 ? 2 : ((c & 0xF0) == 0xE0 ? 3 : 4));
if (i + need > len) tmp[i] = '\0';      // 不完整 → 整块砍掉
```

**修后**:非法 UTF-8 **0 处**,JSON 解析正常 ✅

|---|---|---|

| 4 | `notify` 的消息 | (同类风险) |

> **根源是同一个:中文 3 字节,任何"按字节截断"都可能切断字符。**
> 前 4 次我都是就地改,**这次开始统一用 `utf8Truncate()`** ——
> 但 `log_buffer.cpp` 是底层模块,没引 `script_engine.h`,所以我内联了一段。
>
