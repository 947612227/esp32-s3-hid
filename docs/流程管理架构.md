# 流程管理架构(第 ⑥ 项)

## 一、要解决的问题:三处真相

```
① 板子的 spiffs           = 流程**正文**(原来的权威)
② App 的 SharedPreferences = 流程**状态**(原来的权威)
③ 服务器 board_flows       = **只读备份**(只收不发)
```

**后果**:换手机丢状态 ✅ 换板子丢流程 ✅ 群控无从谈起 ✅

---

## 二、定的架构:**服务器为权威 + 本地缓存**

> 这是三个候选里选的 **C** ✅
> A(纯服务器源)= 板子必须能上外网 ⇒ 和"断网运行"**矛盾** ✅
> B(纯板子源)= 群控做不了 ✅
> **C = 两个都要** ⇒ 代价是要处理同步和冲突 ✅

```
        服务器 flows 表(**权威**)
              ▲   │
     推(改完就推)│   │拉(启动时 + 每次板子连上)
              │   ▼
        App(缓存 + **中转**)
              │   │
     写(板子执行)│   │读(流程列表)
              ▼   ▲
           板子 spiffs(执行端)
```

**⚠️ 为什么必须有 App 中转这一层**:
板子在内网(甚至只有热点)✅ **服务器够不到它** ✅
所以服务器不能推,只能等 App 来拉,再由 App 写进板子 ✅
—— **和"后台点灯"那条路是完全同一个道理** ✅

## 三、数据模型

```sql
CREATE TABLE flows (
  owner      VARCHAR(64)  NOT NULL,   -- 归属:现在=deviceId,以后=用户id
  name       VARCHAR(64)  NOT NULL,
  text       MEDIUMTEXT   NULL,       -- 流程正文
  meta       JSON         NULL,       -- 状态:enabled/定时/频率/绑定App/重复次数
  ver        BIGINT       NOT NULL DEFAULT 1,  -- 每次改 +1
  deleted    TINYINT      NOT NULL DEFAULT 0,  -- **软删除**
  updated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (owner, name),
  KEY idx_owner_ver (owner, ver)
) COMMENT='流程主表(服务器为权威)';
```

**两个设计点**:

**① `meta` 用 JSON 而不是拆列** ✅
App 的 `FlowStore.Meta` 有 **19 个字段**(enabled/appPkg/schedMode/atMillis/freqOn/…)✅
拆成 19 列的话,App 每加一个字段就要改表 ✅ 用 JSON 一处都不用动 ✅
（代价:不能在 SQL 里按状态筛选 ✅ —— 现在也不需要 ✅）

**② 软删除而不是 DELETE** ✅
别的设备靠**增量**同步 ✅ 硬删的话它**永远不知道这条曾经存在** ✅
软删 + `ver+1` ⇒ 增量能拉到 "这条被删了" 这个事实 ✅

## 四、接口

```javascript
GET    /api/v1/app/flows?deviceId=X&since=<ver>
       since=0 → 全量(deleted=0 的);since>0 → 增量(ver > since,含 deleted=1)
       → { ok, ver, full, flows:[{name,text,meta,ver,deleted,updatedAt}] }

POST   /api/v1/app/flows   { deviceId, name, text, meta, baseVer }
       → 成功 { ok, name, ver }
       → 冲突 409 { ok:false, conflict:true, message, server:{...} }

DELETE /api/v1/app/flows/:name?deviceId=X      → 软删除

GET    /api/admin/flows[?owner=X]              → 后台看(列表 + owner 汇总)
```

### ⚠️ 冲突语义(`baseVer`)—— 这里有个容易搞错的点

| baseVer | 含义 | 行为 |
|---|---|---|
| **0** | 「我**没见过**服务器的版本」(新建 / 导入) | **盲写**,不报冲突 |
| **N>0** | 「我**基于第 N 版**改的」 | 服务器 >N 就 **409**,**不覆盖** |

**为什么要这么分**:
新建流程时客户端手里根本没有服务器版本号 ✅ 如果 `baseVer=0` 也报冲突,
那**新建永远失败** ✅

**实测**:
```
① 新建(baseVer=0)      → ✅ ver=1
② 基于第1版改           → ✅ ver=2
③ 再用旧第1版改         → ✅ HTTP 409「服务器上已是第2版(你基于第1版)」
④ 服务器内容没被覆盖     → ✅ 仍是 v2
⑤ 拉最新后重试          → ✅ ver=3
```

## 五、App 端

**新增 `FlowSync.java`**:

```java
FlowSync.pull(act, board, cb)   // 拉增量 → 写本地元数据 + 写板子
FlowSync.push(act, name, text, meta, baseVer, cb)
```

**挂在哪两个地方**:

| 时机 | 调用 | 位置 |
|---|---|---|
| App 启动 / 板子连上 | `FlowSync.pull()` | `MainActivity.maybeFlowSync()` |
| 用户保存流程 | `FlowSync.push()` | `FlowEditActivity.doSave()` |

**⚠️ `maybeFlowSync` 的三个细节**:
1. **不做"板子在不在线"的前置判断** ✅ —— `Board` 没有这个接口 ✅ 而且板子没连上时,拉下来的**元数据**也该写进本地 ✅
2. **失败不置完成标志** ⇒ 60 秒后重试 ✅
3. 成功后 `loadScripts()` 刷新列表 ✅

**⚠️ `doSave` 里用 `baseVer=0`(盲写)** ✅
编辑页手里只有"当前草稿"✅ 没有服务器版本号 ✅
真冲突时服务器**保留它自己的版本** ✅ 下一次 `pull` 会把服务器的内容拉回来 ✅
—— **不会静默丢数据** ✅

**同步进度存在哪**:`SharedPreferences("flow_sync").lastVer` ✅

## 八、⚠️⚠️ 真机联调时揪出的三个 bug(全部已修)

### bug ① `ver` 从 1 开始 ⇒ **增量同步从根上就是坏的** 🔴 最严重

```javascript
// 错的
INSERT INTO flows (owner, name, text, meta, ver, deleted) VALUES (?,?,?,?,1,0)
//                                                              ↑ 每条都从 1 开始
```

**后果**:两条流程的 `ver` **都是 1** ⇒ `MAX(ver)` 永远是 1 ⇒
App 的增量条件 `ver > since` **永远拉不到任何东西** ⇒
**只有首次全量能用**。表现:「服务器上新建了流程,App 重启也下不来」✅

**为什么自测没发现**:我一开始只用 `since=0`(全量)测 ✅ 全量永远是对的 ✅
**一测增量就露馅** ✅

**修**:`ver` 改成 **owner 范围内单调递增**(先查 `MAX(ver)` 再 +1)✅
软删除也一样 ✅ —— 否则别的设备拉不到"这条被删了"✅

**已有数据迁移**:App 里存着 `lastVer=1` ✅ 而服务器上也有 `ver=1` 的流程 ⇒
那条**永远拉不到** ✅ 所以把存量 `ver` **整体 +100** ✅ 逼所有客户端重新全量拉一次 ✅

> **教训:自测一定要覆盖"增量/边界"那条路,不能只测"首次"。**
> 全量对 ≠ 增量对 ✅

### bug ② 板子写入**一次性全丢出去** ⇒ 全超时,而日志还在骗人

```java
// 错的
for (flow : flows) { board.save(...); saved++; }   // 不看结果就 +1
```

**两个问题**:
1. **并发**:`board.save()` 是异步的 ✅ 一次全 submit 之后,Board 的请求队列
   被 20 秒轮询和中继占满(日志里能看到 `Long monitor contention ... 6.069s`)✅
   后面的 save 全超时 ✅
2. **日志在骗人**:`saved++` 不看回调的 `ok` ✅ 所以打印"板子写入 2 条" ✅
   而板子上**一条都没多** ✅ —— 这个假日志让我多花了一轮排查 ✅

**修**:改成**串行写**(每写完一条再写下一条)✅ + **按真实结果计数** ✅

### bug ③ `boardLog()` 写到板子 ⇒ 板子够不到时日志**全丢**

```java
private void boardLog(String line) {
    board.appendLog(line, ...);   // 要经 WiFi 发到板子
}
```

**板子在 AP 模式时手机根本够不到它** ⇒ 这些日志**全丢了** ✅
排查时在 logcat 里一个字都看不到 ✅ **白折腾很久** ✅

**修**:同时写 `Log.i("TouchPad", ...)` ✅ 本地一定有 ✅ 板子能收到就顺便存一份 ✅

### ➕ 附带修掉的崩溃(NPE)

```
FATAL: NullPointerException: LinearLayout.removeAllViews() on a null object reference
	at MainActivity.renderScripts(MainActivity.java:1066)
```

**因果链**:`FlowSync` 启动时拉流程 → 回来后调 `loadScripts()` →
而那一刻 `scriptListBox` **还没被 onCreate 赋值** ⇒ 直接 NPE 崩掉 ✅

**这是潜伏 bug** ✅ 任何"UI 就绪前触发 `loadScripts()`"的路径都会踩 ✅
**修在渲染层**(`renderScripts` / `loadScripts` 开头判空)✅
—— 而不是在每个调用点打补丁 ✅
