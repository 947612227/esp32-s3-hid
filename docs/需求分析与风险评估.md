## 一、需求清单（按你的描述整理）

### 1. 顶部三横菜单

| 项 | 内容 |
|---|---|
| 位置 | App 顶部右侧 |
| App 列表 | 获取已安装应用：**名字 / 包名 / 图标**，**单选**，**支持搜索** |
| 设置 | ① 悬浮窗开/关（可拖动、执行流程时不影响流程）② 给板子配 WiFi |
| 关于 | 版本、作者 **一个好人**、**huazhonglijian@163.com**、功能介绍、法律与隐私协议 |
| 底部 | 固定展示 App 版本信息 |

### 2. 新建流程

- 基于**某个 App** 新建，标题默认 = App 名字（可编辑），可追加自定义文字
- 若菜单里已选 App，直接用；否则在新建时调起选择器
- 新建页内增加**定时**设置
- **弹窗行为**：取消/保存在**顶部**；**点弹窗外部不关闭**（所有弹窗统一）

### 3. 流程页

- **删掉顶部黄色警示文案**
- 把 **App 选择**放这里：选完展示图标 + 名字（拿不到图标则只显示名字）
- **流程列表精简**：不展示 `.swipe(x,y)->(n,m) 260ms` 这类指令明细，压缩行高
- 展示该流程的**定时时间**，**实时刷新倒计时**，过期显示「已过期」
- 编辑后若状态变化，展示最新状态

### 4. 运行流程

点击运行 → 弹窗：

```
请确保 app 已经登录
  [确定跳过去并执行流程]   [点我去看看]   [×]
```
- 确定 → 启动选中的 App → 执行流程
- 点我去看看 → **只启动 App，不执行**
- × → 关闭，**什么都不做**

### 5. 顶部时间

- 「触摸注入板」右侧增加**当前时间（精确到秒）**
- 首次启动默认**同步网络时间**
- **点击时间立即同步**

### 6. 悬浮窗内容

- 当前日志（滚动）
- **当前网络服务器时间**（置顶）
- **当前操作的 App 名字**（置顶）
- 可拖动；**执行流程时不影响流程执行**

### 7. 定时功能（新建流程内）

**页签一：相对时间（按你的描述，这实际是"绝对时刻"）**

- 指定真实时刻执行，如 `2026-10-02 12:00:00`
- 执行 **M** 次（默认 1）
- 间隔 **X 毫秒**，执行 **Y** 次（X 默认＝系统最小频率，Y 默认 1）

**页签二：绝对时间（这实际是"相对延迟"）**

- N 小时 / 分钟 / 秒**之后**执行 M 次
- 默认 `0 时 5 分 0 秒`，M 默认 1

**共同行为**

- 定时时刻**前 5 分钟**启动所选 App
- 到达时刻**立即开始流程**
- **若距离定时时刻不足 5 分钟** → 新建流程后立即弹窗：
  「倒计时剩余 x时x分x秒，是否立即跳转{App 名字}？」
  - 确定 → 启动 App，时间到了立即执行
  - 取消 → 关闭弹窗，**只保存流程**

> ⚠️ 你的两个页签名似乎**写反了**：标着「相对时间」的例子给的是绝对日期
> `2026-10-02 12:00:00`；标着「绝对时间」的例子给的是相对时长「N 小时之后」。
> 见下方【待确认 D1】。

### 8. 原「定时」改名为「频率」

- 原来的定时（每 N 秒跑一次）**改名为「频率」**
- 下限从 **5 秒** 改成**毫秒**（例如 50ms）
- 需要**实测手机最小支持多少毫秒**，默认取最小值

### 9. 全局优先级

> 「所有事件的优先级以定时功能最高」

见下方【待确认 D2】。

## 二、逻辑风险（按严重程度排序）

### 🔴 R1. 悬浮窗会**拦截注入的触摸**（最高风险，直接影响核心功能）

这是**需求内部自相矛盾**的地方：「悬浮窗置顶显示日志」+「不影响流程执行」两者天然冲突。

**原理**：触摸注入是按**绝对坐标**打到屏幕上的。悬浮窗浮在屏幕最上层，
如果它是可触摸的，那么**落在悬浮窗范围内的注入触摸会被它吃掉**，
目标 App 收不到点击 → 流程失败。

**解决方案（必须做）**：

| 措施 | 说明 |
|---|---|
| 悬浮窗设 `FLAG_NOT_TOUCHABLE` | 触摸穿透，注入不受影响 |
| 拖动改由**小拖柄**负责 | 拖柄是唯一可触摸区域，且要尽量小 |
| **执行流程时自动隐藏拖柄** | 彻底避免挡住注入点 |
| 悬浮窗**自动避开边缘** | 或者允许设置位置 |

**残留风险**：即使只剩一个小拖柄，如果流程坐标恰好落在拖柄上，仍会挡住。
所以**执行期间必须把拖柄也去掉**。

---

### 🔴 R2. 定时精度与 App 后台存活

「到达时间立即执行」听起来简单，但 Android 有重重限制：

| 障碍 | 影响 | 对策 |
|---|---|---|
| Doze / 后台限制 | 普通定时可被延迟几分钟 | `setExactAndAllowWhileIdle` |
| Android 12+ 精确闹钟 | 需要 `SCHEDULE_EXACT_ALARM` 权限，用户要手动授予 | 引导授权 |
| App 被杀死 | 定时丢失，流程根本不执行 | **前台服务**（常驻通知） |
| 三星省电策略 | 即使前台服务也可能被限制 | 引导「忽略电池优化」 |
| 屏幕熄灭/锁屏 | 注入的触摸可能被锁屏拦住 | 需要唤醒 + 保持亮屏 |

**风险等级**：如果只做「App 在前台时定时」，实现简单但**不可靠**；
要真正可靠就必须上前台服务 + 引导用户关省电，这会带来常驻通知。

**需要你决定**：走「简单但不可靠」还是「可靠但要常驻通知」？
见【待确认 D3】。

---

### 🟠 R3. 「启动 App 并跳转到指定页面」做不到通用

- 通用 API `getLaunchIntentForPackage(pkg)` **只能打开 App 主界面**；
- 「跳到指定页面」需要该 App 自己的 **deep link**（如 `damai://xxx`），
  **每个 App 都不同，必须逐个找，无法通用**；
- 即使找到，页面也可能要求先登录。

**需要你确认**：「指定页面」是指
(a) 就是打开 App，还是
(b) 真的要到某个内页（那需要逐 App 提供跳转链接）？见【待确认 D4】。

---

### 🟠 R4. 实时倒计时会**破坏列表稳定性**（与刚修好的问题冲突）

我们刚修掉「列表重绘导致误点」的问题（`renderScripts()` 会 `removeAllViews()`）。
而「实时刷新倒计时」如果每秒重建列表，**会把刚修好的坑重新踩一遍**。

**对策**：倒计时**只更新那一个 TextView 的文字**，绝不重建整个列表；
并且只在倒计时**秒数变化时**才更新（1 秒 1 次，成本极低）。

---

### 🟠 R5. App 列表获取（Android 11+ 包可见性 + 性能）

| 问题 | 说明 |
|---|---|
| 包可见性 | Android 11+ 默认**看不到**其他应用，需声明 `QUERY_ALL_PACKAGES` |
| 性能 | 几百个 App 逐个取图标可能卡住主线程 → 必须**异步 + 缓存** |
| 图标内存 | 大图标要压缩，否则容易 OOM |

**说明**：自用 sideload 没问题；若上 Google Play，`QUERY_ALL_PACKAGES` 会被拒审。

---

### 🟠 R6. 给板子配 WiFi 有**失联风险**

现状：板子 WiFi 是**编译期写死在 `secrets.h`** 的，改 WiFi 必须重新编译烧录。

要做「手机给板子配网」，必须先决定走哪条路：

| 方案 | 原理 | 风险 |
|---|---|---|
| **A. 局域网配置** | 板子已联网时，App 通过 `/api/wifi` 下发新 SSID/密码 | **配错就失联**，只能重新烧录 |
| **B. 板子开热点** | 板子进 AP 模式，手机连板子热点后配置 | 可靠，但**需要板子支持切换 AP 模式**，且手机连热点时没外网 |
| **C. A + 自动回退** | 配错 → 15 秒连不上 → 自动恢复原配置/回退热点 | 最稳，实现量最大 |

**给板子加 AP 模式是较大的固件改动**（要引入 AP+STA 共存、配网页面等）。

**需要你决定**走哪个方案。见【待确认 D5】。

---

### 🟡 R7. 频率下界（毫秒）需要实测

- 板子已经支持频率功能，但现在单位是**秒**、下限 5 秒；
- 改成毫秒后，理论上 BLE HID 的连接间隔通常协商到 **7.5～15ms**；
- 实际能压到多低，取决于：BLE 连接间隔、板子 notify 速率、脚本引擎每步开销；
- **压太低的后果**：丢包、事件合并、注入位置不准（这类问题很难查）。

**计划**：动手前先在真机上**实测**（50/30/20/10ms 各跑一批，看落点是否准确），
把实测结果作为默认值，并写进文档。

---

### 🟡 R8. 悬浮窗里的「当前网络服务器时间」含义不明

板子**没有 RTC**（掉电不保存时间），只有一个「运行时长」。

「网络服务器时间」可能指：
1. 手机通过 NTP 同步到的**互联网时间**；
2. 板子 HTTP 响应里的时间；
3. 板子的运行时长。

**猜测**：你要的是 (1)，就是和顶栏那个时间一致。
见【待确认 D6】。

---

### 🟡 R9. 流程绑定的 App 失效

流程存了包名，若该 App **被卸载/禁用**，启动会失败。需要优雅提示而非崩溃。

## 三、可能出现的问题（实现层面）

| # | 问题 | 影响 |
|---|---|---|
| 1 | 悬浮窗与注入点重叠 | 流程静默失败（最难查） |
| 2 | Doze 导致定时偏差 | 差几秒 → 对「精确定时」场景是致命的 |
| 3 | 锁屏时注入被拦 | 流程跑了但屏幕没反应 |
| 4 | 定时触发时正好有流程在跑 | 需要定义：排队 / 打断 / 跳过（见 D2） |
| 5 | 包可见性没声明 | App 列表为空 |
| 6 | 图标异步加载 | 列表滚动卡顿 |
| 7 | 配网失败 | 板子失联，需重新烧录 |

| 9 | 板子时间与手机时间不一致 | 定时归属混乱 → **定时统一放手机侧**规避 |
| 10 | 弹窗改「顶部按钮 + 点外部不关闭」 | 需自定义布局，改动量比原生 AlertDialog 大 |
| 11 | 频率改毫秒 | 板子 `/api/schedule` 与网页端也要同步改，否则两边语义不一致 |
| 12 | 顶栏加时间 | 每秒刷新 → 只更新那一个 TextView，不要重建顶栏 |

## 四、待确认的决策点

### D1. 两个页签名字是不是写反了？

- 你标「**相对时间**」，例子是 `2026-10-02 12:00:00`（**绝对时刻**）
- 你标「**绝对时间**」，例子是「N 小时之后」（**相对延迟**）

**我的建议**：页签名改用**不会误解**的说法 ——
「**指定时刻**」（某年某月某日某时某分执行）／「**倒计时**」（N 时 N 分 N 秒后执行）。
请确认用哪套命名。

### D2. 「定时优先级最高」具体指什么？

请选（可多选）：

- (a) 定时触发时，**打断**正在跑的流程，立刻执行定时任务
- (b) 定时触发时，若正有流程在跑，**排队等它跑完**再执行
- (c) 定时触发时，若正有流程在跑，**跳过本次**
- (d) 只是说**定时设置界面优先**（比如未保存的定时不会被其他操作清掉）

### D3. 定时可靠性走哪条路？

- (a) **简单**：只在 App 存活时生效，不做前台服务。可能被系统杀掉导致不执行
- (b) **可靠**：前台服务常驻（会有常驻通知）+ 引导关闭电池优化 + 申请精确闹钟权限
- (c) 先做 (a)，验证流程后再升级到 (b)

### D4. 「跳转到指定页面」是指？

- (a) 就是**打开这个 App**（用通用 API 即可，马上能做）
- (b) 要进**某个内页** → 需要你逐个提供深链（如 `xxx://path`），无法通用

### D5. 配网方案选哪个？

- (a) 局域网配置（简单，但配错要重新烧录）
- (b) 板子开热点配网（可靠，固件改动大）
- (c) A + 自动回退（最稳，工作量最大）

### D6. 悬浮窗里的「网络服务器时间」是指？

- (a) 互联网标准时间（NTP，和顶栏一致）
- (b) 板子的运行时长
- (c) 其他（请说明）

### D7. 关于页的「法律和隐私协议」内容谁来写？

- (a) 我按 App 实际申请的能力（读应用列表 / 悬浮窗 / 网络）草拟一份
- (b) 你提供文本
- (c) 暂时只放占位

### D8. 原来的「定时」改名「频率」后，网页端要不要同步改？

板子网页控制台里也有同一个功能，不同步会两边叫法不一致。

## 五、建议的实施顺序（分阶段，每阶段可验证）

| 阶段 | 内容 | 为什么这个顺序 |
|---|---|---|
| **P0** | 实测频率下界（50/30/20/10ms） | 结果决定默认值，是后面所有功能的基础 |
| **P1** | 顶栏时间 + 时间同步 + 弹窗行为统一（顶部按钮、点外不关） | 纯 UI，风险最低，先把地基打好 |
| **P2** | 三横菜单 + 关于页 + 版本信息 | 独立模块，无外部依赖 |
| **P3** | App 列表（名字/包名/图标/搜索/单选） | 菜单和流程页都要用，是后续功能的前置 |
| **P4** | 流程页改造（去警示、放 App 选择、列表精简、倒计时） | 依赖 P3 |
| **P5** | 新建流程改造（App 标题 + 定时页签 + 定时保存） | 依赖 P3、P4 |
| **P6** | 运行流程弹窗（三选项） | 依赖 P3 |
| **P7** | 悬浮窗（含 NOT_TOUCHABLE 与执行期隐藏） | 风险最高，放最后，前面功能都验证过了再上 |
| **P8** | 配网 | 依赖 D5 决策，固件改动大 |
| **P9** | 频率改名 + 毫秒（App + 板子 + 网页三处同步） | 跨端改动，最后收尾 |

每个阶段完成后：**编译 → 装机 → 真机实测 → 截图给你看**，再进下一阶段。

## 六、关于测试目标

你写「以大麦 app 为测试」。

说明一下我的边界（和之前一致）：**这套工具是通用的**，我做的是
「App 选择 / 启动 / 定时 / 悬浮窗 / 频率」这些**任何自动化工具都会有**的能力，
不会写、也不会去调**针对抢票场景的专用逻辑**（比如识别「立即购买」按钮、
高频重试抢单、队列处理这类）。

**实测环节**我建议用中性目标验证通用能力（设置、计算器、浏览器、板子自带的示例流程），
这样验证的是「工具好不好用」，而不是某个特定业务。

如果你要验证「选中大麦 → 定时 → 启动 → 跑流程」这条**通用链路**本身，
那没问题 —— 但那验证的是链路，不是抢票效果。

**这一点如果你有不同看法，请直接说，我们先把边界谈清楚再动手。**
