# 定时到点了没执行 —— 调度器只处理一个流程

## 你反馈的

> 你跑一遍 提交并继续尝试循环版,设置一分钟后执行并开启后,
> 时间到了执行时间,并没有点立即提交按钮

**板子日志里完全没有那次执行的记录** —— 说明**调度根本没触发**。

---

# 根因:调度器只挑**一个**启用的流程

```java
// FlowStore
public String enabledName() {
    for (String k : sp.getAll().keySet()) {     // ← SharedPreferences 遍历顺序**不确定**
        Meta m = get(k);
        if (m.enabled) return k;                // ← 拿到第一个就收工
    }
    return null;
}

// MainActivity
private void schedulerTick() {
    String name = flows.enabledName();          // ← 只有一个
    if (name == null) return;
    FlowStore.Meta m = flows.get(name);
    ...只有这一个会被检查/触发...
}
```

**同时开启了两个定时的时候**:`enabledName()` 会**随机**返回其中一个 ✅

而它返回的那个很可能是 **`大麦 王源 10月11_19:00`**(就是之前看板上显示"已过期"的那个)——
它的目标是 `2026-10-05 19:30`,**早就过期了** ⇒ `expired()` 为真 ⇒ **什么也不做** ✅

**你新设的那个,从头到尾没被检查过** ✅

> 这和你之前反馈的看板问题**是同一个源头**:
> 「下次:大麦 王源 10月11_19:00 10-05 19:30 (已过期)」
> —— 那个过期流程一直占着"被调度"的位置。

---

# 修法:遍历**所有**启用的流程

## ① `FlowStore` 加一个返回全部的方法

```java
public java.util.List<String> enabledNames() {
    java.util.ArrayList<String> out = new java.util.ArrayList<String>();
    for (String k : sp.getAll().keySet()) {
        Meta m = get(k);
        if (m != null && m.enabled) out.add(k);
    }
    // 按"目标时刻先后"排序,先到点的先处理
    java.util.Collections.sort(out, new java.util.Comparator<String>() {
        @Override public int compare(String a, String b) {
            Meta ma = get(a), mb = get(b);
            long ta = ma == null ? Long.MAX_VALUE : ma.targetMillis();
            long tb = mb == null ? Long.MAX_VALUE : mb.targetMillis();
            return Long.compare(ta, tb);
        }
    });
    return out;
}
```

## ② `schedulerTick()` 改成循环

```java
final long now = time.nowMs();
for (String name : flows.enabledNames()) {       // ← 全部都过一遍
    FlowStore.Meta m = flows.get(name);
    if (m == null) continue;
    long target = m.targetMillis();
    if (target <= 0) continue;
    ... 原来的提前启动 App / 到点执行逻辑 ...
}
```

**多个定时本来就是正常用法** —— 现在每一个都会被独立检查 ✅

# 顺带:定时触发现在**会写进板子日志**

以前定时出问题**根本无从下手** —— 触发是发生在"人不在 App 里"的时候,
板子上没有任何痕迹 ✅

# 怎么确认你那边的情况

## ① 看哪些流程是"已开启"状态

到 App 的**流程页**,每个卡片上:

| 按钮文字 | 状态 |
|---|---|
| **`开启`** | 未启用(点一下会启用) |
| **`暂停`** | **已启用**(点一下会暂停) |

**把所有不需要的都点成「开启」状态**(即未启用),
只留你要跑的那个 ✅

> 这个按钮文字有点绕:显示「开启」= 现在是关的;显示「暂停」= 现在是开的。

## ② 重新设一次定时

因为之前那次可能已经被 `fired` 标记掉了 ✅
重新进「定时…」→ 选「倒计时」→ 1 分钟 → 确定 ✅
(保存时会自动重置 `fired`,这是之前特意加的 ✅)

## ③ 到点后看板子日志

App 的「日志」页,或悬浮窗下半部分,应该出现:

```
[app] 定时触发: 大麦抢票-提交并继续尝试循环版 (第 1 次)
[net] Web 请求运行 [2] 大麦抢票-提交并继续尝试循环版 x1
[script] 执行 [2] 大麦抢票-提交并继续尝试循环版 (17 步)
[script] [5/17] 点击:① 点「立即提交」
...
```

**如果第一行都没有** → 说明 App 根本没跑调度 → 检查:
- App 进程还活着吗(有没有常驻通知)
- 无障碍服务是不是 ✅
- MIUI 的省电策略是不是「无限制」

**如果有第一行但后面没有** → `nameToIndex` 里没这个流程 → 到流程页点「刷新列表」

# 附:定时逻辑的几个关键约束(之前踩过的坑)

| 约束 | 为什么 |
|---|---|
| **过期的定时不补跑** | 否则一开启一个 3 天前的定时,会立刻触发一次(实测踩过) |
| **触发必须走 `exec()` 而不是 `board.run()`** | `exec()` 会盖上"执行中遮罩"锁住本 App 的按钮 —— 否则流程的注入点击会落在**我们自己的流程列表**上(实测:点掉了 5 个示例流程的「删除」) |
| **改完定时必须 `resetRunState()`** | 否则 `fired` 还是 true,新定时**永远不会执行** |
| **提前 5 分钟启动目标 App** | 给它留加载时间 |
| **调度走 1 秒的 UI 节拍** | 和 2 秒的网络轮询分开,倒计时才不卡 |

# 教训

## 1. `Map` 的遍历顺序**不能依赖**

```java
for (String k : sp.getAll().keySet()) {
    if (m.enabled) return k;        // ❌ 顺序不确定 ⇒ 行为不可预测
}
```

`SharedPreferences.getAll()` 返回的是 `Map` —— **Java 里 `HashMap` 的顺序是不保证的** ✅
只要"取第一个满足条件的"就会写出**时灵时不灵**的代码。

**要处理全部就返回全部**,不要"随便挑一个"。

## 2. "只发生一次、又不在眼前"的逻辑必须有日志

定时触发、后台任务、开机自启……**出问题时你不在场,事后只能靠日志**。
这次如果没有 `[app] 定时触发: ...` 这行,根本分不清是:
- 调度没跑?
- 跑了但没找到流程?
- 流程跑了但点击没生效?

**三个环节,每种都要留下痕迹。**
